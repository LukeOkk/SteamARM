Part 1: the hang (MEASURED)
---------------------------
mksh blocks SIGCHLD around fork and waits for the child's SIGCHLD in
rt_sigsuspend with SIGCHLD let through. The SIGCHLD was lost in two places:

a. XNU binds a process-directed signal to one thread when it is posted: a
   thread that does not block it (or waits for it in sigwait); when every
   thread blocks it, the process's first thread, where it stays. Linux
   keeps it in the process's shared pending set for the first thread that
   unblocks it. Under lxrun the first thread is the host main thread, which
   blocks every signal for good (runtime/main.c). A SIGCHLD that came while
   the guest blocked it, or while the runtime was in one of its
   all-signals-blocked sections (the thread table lock every rt_sigprocmask
   takes), was never delivered. tests/elf/sig_stranded.c (freestanding,
   raw syscalls: SIGCHLD of a child that exits while blocked, the same with
   rt_sigsuspend as the wait, a kill() from a child while SIGUSR1 is
   blocked), run here:
     main's lxrun (7492467):   == sig_stranded: 0 ok, 3 mal
       MAL chld: ... not delivered within 2 s of the unblock
       MAL suspend: rt_sigsuspend woke only for the 2 s watchdog
       MAL kill: ... not delivered within 2 s of the unblock
     this branch's lxrun:      == sig_stranded: 3 ok, 0 mal
   Fix (1519c69): runtime/signal.c lxrt_signal_rescue_stranded. The main
   thread looks at its pending set on every turn of its loop (window.m: at
   most 20 ms apart; main.c's LXRT_NO_PUMP loop: 10 ms), and takes each
   signal with the runtime's handler by unblocking it for a moment;
   host_handler on a non-guest thread hands it to a guest thread with
   pthread_kill: the first whose Linux mask (runtime/thread.c now notes it
   on rt_sigprocmask, rt_sigsuspend and a handler's return) lets it
   through, else the first guest thread, where it stays pending until
   unblocked. Signals at SIG_DFL are left alone.
b. FEX updates its emulated mask before the host mask
   (SignalDelegator::GuestSigProcMask), and a guest handler runs with a
   host mask narrower than the guest's; a signal that lands in between is
   taken from the host and only recorded in PendingSignals, re-raised by
   CheckForPendingSignals when the guest unmasks it with rt_sigprocmask.
   GuestSigSuspend never looked there before the host sigsuspend (the
   previous session's instrumented FEX: "SIGCHLD -> pending 10000", then
   "sigsuspend set=80000000 pend=10000" and no wake). Fix:
   patches/fex-lxrt-sigsuspend-pending.patch raises each pending signal the
   suspend mask lets through again (tgkill to itself, blocked on the host)
   so the host sigsuspend delivers it and returns; the host handler clears
   the PendingSignals bit as it delivers (VERIFIED IN SOURCE,
   SignalDelegator.cpp), so it is not delivered twice.
   GuestSigTimedWait does the same for the signals of its set.

Not fixed, stated (VERIFIED IN SOURCE, not measured): a stranded signal
that no guest thread accepts goes to the first guest thread and stays
pending there. A program whose OTHER thread later waits for it in
sigwait/sigtimedwait (a dedicated signal thread, as ART's signal catcher)
would not get it, and the runtime's rt_sigtimedwait (fex_support.c) does
not note its thread as accepting the waited set. XNU itself targets a
thread that is in sigwait when the signal is posted, so this needs the
signal to arrive while that thread is busy. Linux would hand it to
whichever thread wants it first.

Two limits found here (MEASURED), both from 32-bit bionic keeping thread
ids in 16 bits (pthread_mutex_t is 4 bytes on 32-bit):
a. 32-bit bionic refuses to start when the main thread's tid is above
   65535 (the message is in the image's lib/bionic/libc.so, not in
   lib64's). Under lxrun that tid is the Mac's pid, which runs up to
   99999. In suite run 6 (05:28, the Mac's pid counter near 84000-95000)
   dalvikvm32 and dex2oat32 printed "Limited by the size of
   pthread_mutex_t, 32 bit bionic libc only accepts pid <= 65535, but
   current pid is 84368" (94454 for dex2oat32) and then hung until the
   test's deadline instead of exiting; the i386 probe hung the same way
   (the check kept no line of its output). At 05:36, after the counter wrapped
   (pids near 11000), the audio HAL and zygote_secondary started.
   tests/android/run.sh now names such runs expected failures.
b. Every other thread's tid is 200000 + pid * 10000 + n
   (runtime/thread.c next_tid, chosen so a tid never equals a Darwin pid).
   tests/android/i386_rmutex.c (new; the image's 32-bit bionic, a second
   thread takes a recursive and an error-checking mutex):
     main tid 21107
     thread tid 211270001: recursive lock 0, relock (trylock) 16, unlock 1 -1;
       errorcheck lock 0, unlock 1
     == i386_rmutex: MAL
   EBUSY on its own recursive mutex, EPERM unlocking its own mutex; a first
   version that printed from the thread never returned (stdio's recursive
   lock). zygote_secondary, dalvikvm32 and dex2oat32 got through their runs
   regardless, but any 32-bit Android code that uses a recursive mutex off
   the main thread will hang. An expected failure in tests/android/run.sh.
   The fix is tids (and a main-thread pid) below 65536 for 32-bit bionic
   guests that stay unique across processes: a system-wide id allocator in
   the runtime. Not done. i386 glibc has no such limit (the Steam client).

Part 5: a /dev/input per stack (MEASURED; commit 29c324b)
---------------------------------------------------------
runtime/evdev.c mapped every guest's /dev/input to /tmp/lxrt-input, where
steamarm-inputd publishes the controllers; Waydroid's composer makes its
input FIFOs (wl_pointer_events, wl_keyboard_events, ...) in /dev/input
for InputFlinger's EventHub, so they landed next to the controllers and
two Android roots would have shared them. LXRT_INPUT_DIR=<absolute host
directory> gives a guest (and what it runs: the variable is in the
environment the runtime passes on) its own /dev/input; unset, it is
/tmp/lxrt-input, so the Steam controller path is unchanged.
run-android-display.sh and android-boot.py give their stack <state>/input.
Review: the runtime does not carry LXRT_INPUT_DIR into a guest's execve
when the guest drops it from the environment, as with LXRT_BINDER_DIR and
LXRT_PROPERTY_DIR (VERIFIED IN SOURCE, process.c); Android's services get
it from android-boot.py's environment.
  tests/android/run.sh: "LXRT_INPUT_DIR: a composer-style FIFO writer and
  an EventHub-style reader (x86-64, FEX) meet in their /dev/input; another
  stack's does not have it (50 EV_SYN, 50 EV_KEY, 50 EV_REL (sum 1275),
  0 EV_ABS)".
  tests/elf/run.sh: the check "LXRT_INPUT_DIR default" failed the first
