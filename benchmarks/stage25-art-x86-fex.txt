Stage 25 -- x86-64 Android's ART under FEX: Java runs, zero VM (2026-09-29)
=============================================================================

ZERO-VM. No virtual machine, no guest kernel. Host: Mac mini M4, 16 GB,
macOS 27.0 (26A428). Base commit 37f5bce. Every Android binary below is an
unmodified x86-64 (or i386) file from Waydroid's LineageOS 18.1 x86_64 image,
run by SteamARM's FEX (an aarch64 Linux program) under lxrun, as an ordinary
macOS process. Nothing was signed in to, no Google component was downloaded,
no Steam client was started, scripts/run-app.sh was not called. The arm64
Android root (/Volumes/SteamARMAndroid/root, in use by another agent's binder
tests) was not modified; the only thing run from it was `toybox true`, for a
memory figure (it writes nothing). The shared FEXServer (Ubuntu rootfs) was
used read-only by the i386 and Steam-root regression runs; the x86_64 root
has a FEXServer of its own, started and stopped by this session's scripts.
Home paths are written as ~. Labels: MEASURED, VERIFIED IN SOURCE, UPSTREAM
DOCUMENTED, HYPOTHESIS, UNKNOWN.

The question
------------
Native arm64 ART cannot start under lxrun: it keeps object references in 32
bits, so its heap and boot image must be mapped below 4 GiB, and macOS maps
nothing there in an arm64 process (stage25-android-userspace.txt). FEX
translates every guest address, and SteamARM's FEX already has a "64-bit low
window" (guest 0 < x < 4 GiB at host 0x8000000000 + x; stage7-guest-base.txt).
HYPOTHESIS tested: x86-64 ART, from the x86_64 build of the same Android,
maps its heap below 4 GiB of GUEST address space under FEX and runs a dex.

Result (MEASURED)
-----------------
1. Yes. dalvikvm64 (x86-64 ART, Android 11) runs Java under FEX with the low
   window forced on (FEX_LOWWINDOW=1): "Hello from Java on ART, no VM",
   java.vm.name=Dalvik, os.arch=x86_64. Objects live at guest 0x12c03c50
   (ART's own preferred heap base, 0x12c00000), a 4 MiB array at
   0x7bbfa000, and Object.class, a boot-image object, at 0x708d01e0 and
   0x6f14f1e0 in two runs (ART_BASE_ADDRESS 0x70000000 plus its random
   delta); tests/android/java/HeapRef.java reads the 32-bit references.
   Without the window (FEX_LOWWINDOW=0) the same run fails exactly as native
   arm64 ART does ("heap.cc:493 ... Failed anonymous mmap(0x0, 67108864 ...):
   Out of memory").
2. Interpreter and JIT both give the Mac JVM's results: Loop (-Xint, 2 M
   steps) -6435145747647352456 and Loop (JIT, 20 M steps)
   6336216350770228723 in every round; a JIT code cache that is collected and
   reused (128 KiB) gives the JVM's checksum -1445667666822057310. dex2oat64
   compiles hello.dex to an odex (0.85 s) and the AOT code runs correctly.
3. Costs: toybox start 0.12 s (native arm64: 0.03-0.06 s); dalvikvm64 Hello
   0.98 s and 222 MB peak RSS; ART's JIT code runs the Loop at 77 ms/round
   against 62 ms for HotSpot C2 on the same M4; the interpreter at 156
   ms/round against 46 ms for HotSpot's.
4. It took six runtime changes (R1-R6), a passwd entry in the root (R7), a
   script to build the root (--arch x86_64), a runner, the image's own
   linkerconfig run under FEX, and three FEX patches (P1-P3). Two of the FEX patches fix latent bugs that
   affect every FEX guest on SteamARM, not only Android: deferred signals
   were never delivered (P3), and SMC tracking missed writes through a
   second view of shared memory (P2).
5. The trade-off (section T): this path runs Java/Kotlin apps and apps with
   x86-64 (or, untested, x86) native code. An APK whose only native code is
   arm64-v8a has nothing to run here: the x86_64 image has no
   arm64-to-x86 native bridge (ro.dalvik.vm.native.bridge=0; Intel's Houdini
   and Google's libndk_translation are proprietary and absent). ARM64-first
   stays the mission: arm64 native Android still needs the ART heap fix of
   docs/ANDROID_RUNTIME_ARCHITECTURE.md for the native root.

How it runs (scripts/run-android-x86.sh)
----------------------------------------
env -i; LXRT_ROOT=<root>; TMPDIR=/tmp (the HOST directory where the runtime
materialises Linux abstract sockets); XDG_RUNTIME_DIR=/data/local/tmp;
HOME=/data/local/tmp; FEX_ROOTFS=/ (the root IS the x86 tree);
FEX_GUESTBASE=1 FEX_LOWWINDOW=1 FEX_SMCCHECKS=mtrack;
FEX_SERVERSOCKETPATH=steamarm-android-<12 hex of the root path's
sha1>.FEXServer.Socket; then init.environ.rc's ANDROID_*, BOOTCLASSPATH,
DEX2OATBOOTCLASSPATH.
FEXServer: a FEX client takes its rootfs from the server it connects to
(VERIFIED IN SOURCE, Source/Common/FEXServerClient.cpp SetupClient), and the
shared server serves the Ubuntu rootfs. So this root has its own server: own
socket name, own lock (Server.lock under HOME), started through the lxrt-emu
loader (ld-linux-aarch64.so.1 --library-path /usr/lib/lxrt-emu FEXServer),
detached, --persistent=60, its PID in /data/local/tmp/.fexserver.pid;
--server-stop acts only on a PID whose process is an lxrt-emu FEXServer
with this root as its LXRT_ROOT.
FEX_LOWWINDOW=1: SteamARM's FEX gives the low window only to ET_EXEC and
wine processes; Android's programs are PIE, so it is forced. The FEX log
then says "GuestBase: 64-bit guest (ET_EXEC), low window at host
0x8000000000" for a PIE too (the message's wording, not a mistake in the
mode).

Changes
-------
Runtime (runtime/, commit "runtime: what x86-64 Android's bionic and ART
need under FEX"):
R1  getrlimit/setrlimit, asm-generic 163/164, as prlimit64 of pid 0.
R2  /proc/self/stat field 28 (startstack): the initial stack pointer the
    runtime built (main.c), or, when a writable MAP_GROWSDOWN mapping is made
    (FEX's stack for the x86 program, ELFCodeLoader.h), an address in it,
    the guest's view under a guest base. Linux shows the process its own
    startstack; the runtime printed 0.
R3  prlimit64 (and so R1): Darwin's RLIM_INFINITY is reported as Linux's
    (~0) and taken back from it; the new limit is read before the old one is
    written (Linux allows the same buffer for both).
R4  AF_UNIX SOCK_DGRAM (and SEQPACKET, a datagram pair here) sockets get
    212992-byte send and receive buffers, Linux's net.core defaults.
R5  madvise with a guest base and an address below 4 GiB acts on base +
    address (the same unambiguous rule gbase.c applies to pointer arguments:
    no host memory lives below 4 GiB); a range running past 4 GiB is split
    at 4 GiB (the window's part, then identity).
R6  getgroups/setgroups.
R7  (scripts/mkandroidroot.sh) /system/etc/passwd and group entries
    "system_steamarm" for the Mac's uid and gid.

FEX (patches/, applied by scripts/build-fex-host.sh after the existing
eight; built for this record in a private work dir, STEAMARM_BUILD=<scratch>,
Release only, 19-23 s per build on the M4; reproducible: the same inputs gave
the same FEX-emu sha256 twice):
P1  fex-lxrt-lowwin-hint.patch: in the 64-bit low window a plain hint below
    4 GiB is tried as MAP_FIXED_NOREPLACE in the window before the host.
P2  fex-lxrt-smc-mprotect-mirrors.patch, two parts:
    1. a guest mprotect making a shared view writable while another view of
       the same memory is executable leaves that view's host pages read-only
       (the guest sees them writable; the range goes read-only first and
       only the rest is opened, so no page is ever writable unseen); each
       first write faults and is flushed precisely;
    2. the fault handler's shared-memory branch flushes and unprotects the
       whole 16 KiB SMC page of every mirror, not 4 KiB (unprotecting 4 KiB
       made the whole host page writable).
    A first version invalidated every mirror's translations at each such
    mprotect: correct, but JitChurn with the default cache went from 1.72 s
    to 7.61 s (5 runs, median), since ART flips the whole cache's view for
    every compiled method. Replaced by the above (1.74 s).
P3  fex-lxrt-interrupt-page.patch: InterruptFaultPage (and the thread
    object's alignment) 16 KiB instead of FEX_PAGE_SIZE.
A read-only review of the diff (Codex) found, and this record's last FEX
build fixes: an overflow in P1's below-4 GiB test (addr + length for a hint
near 2^64), the order of P2 part 1 (it first opened the range and then
re-protected it, leaving a window), madvise ranges across 4 GiB (R5), and
one FEXServer socket name for every root (run-android-x86.sh). Only the
x86_64 root carries this FEX (/usr/lib/lxrt-emu/FEX, FEX-emu sha256
08daa48ab5e9...; FEX 8787aad9988f...). /tmp/lxrt-root, the Steam root and
~/SteamARM-build/out were not rebuilt or reinstalled.

T. The trade-off
----------------
- What it makes possible: Java/Kotlin apps (dex runs on x86-64 ART), and
  apps that ship x86-64 native libraries, all zero-VM, all through the
  existing FEX. The image's 1,217 i386 files (the x86 half of zygote64_32)
  could run under FEX's 32-bit mode as well (UNTESTED).
- What it does not: apps whose native code is arm64-v8a only. The x86 image
  has no native bridge (ro.dalvik.vm.native.bridge=0, no Houdini or
  libndk_translation file); both translators are proprietary and SteamARM
  must not bundle them. On a Mac that is the painful part: the CPU is arm64
  and the app's arm64 code would have to be translated to x86 to be
  translated back by FEX. How many Play apps ship ARM ABIs only is UNKNOWN
  here (HYPOTHESIS: many games do); the F-Droid sample above is not
  representative of Play.
- Costs: every Android process is a FEX process (~0.1 s start, ~15 MB, a
  JIT on top of ART's JIT), and ART's generated code is translated again;
  measured 1.23x HotSpot for JIT'd code and 3.4x for the interpreter.
- ARM64-first: the native arm64 root stays the target for arm64 apps and
  needs the ART heap work in docs/ANDROID_RUNTIME_ARCHITECTURE.md. This path
  is the zero-VM way to run Java today, and a way to develop binder,
  properties, init and zygote against a working ART while that happens.

What was not done
-----------------
- No zygote, system_server, binder, property service or init: dalvikvm64
  and dex2oat64 only. linkerconfig's output is the "legacy" layout.
- Graphics, input, audio: nothing (the vendor image's Mesa is for x86 GPUs).
- FEX was not installed for the Steam side; building it with
  scripts/build-fex-host.sh now applies P1-P3, and install-fex-host.sh would
  put it in the shared roots: run the Steam/Proton smoke tests first.
- P2's cost is one fault per 16 KiB page written after each mprotect that
  makes such a view writable; not measured separately (JitChurn with the
  default cache: 1.72 s unpatched, 1.74 s with P2).
- Not changed after the review: a Linux limit value from 2^63-1 up is
  "no limit" on Darwin and reads back as RLIM_INFINITY (R3).
- 32-bit guests: P3 applies to them too (the same thread object); P2 part 2
  does not (their SMC page stays 4 KiB; tests/elf/i386_smc_subpage.c is
  still an expected failure).
