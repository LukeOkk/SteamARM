Stage 27 (Android display) -- Wayland on the Mac through lxrun, and Android's SurfaceFlinger in a macOS window (2026-09-29)
=======================================================================================================================

ZERO-VM. Every process below is an ordinary macOS process: lxrun running a
Linux aarch64 program, or lxrun running FEX running an x86-64 program. No
VM was started or proposed. Host: Mac mini M4, macOS 27.0. Base commit
bc27c17. The X server on :2 (scripts/run-x11-native.sh, SteamARM-X11.app)
was already running and was not restarted or stopped. Another session ran
its own Android stack in /Volumes/SteamARMAndroid/root-x86_64 at the same
time (its own binder hub, property service and logd stand-in); this one
worked in an APFS clone of that root (/Volumes/SteamARMAndroid/x86disp,
a few seconds and no space to make) with private binder and property
directories, so neither saw the other. No Steam client, no account, no
Google software; nothing downloaded is committed (the Weston root is built
from pinned Fedora packages by a script; the Android images are Waydroid's,
as at stage 25).

VERIFIED IN SOURCE (libwayland-server, shm.c, shm_pool_grow_mapping): on
Linux a pool grown by wl_shm_pool.resize is remapped with
mremap(MREMAP_MAYMOVE); the client's fd is closed after the first mmap, so
nothing else leads back to the file. lxrun's mremap handled anonymous
memory only.
Fix (runtime/mremap.c, runtime/dispatch.c): every MAP_SHARED file mapping
(host-page aligned, not executable) is recorded with a Mach fileport of its
descriptor (fileport_makeport: keeps the open file, takes no descriptor
number the guest could see); mremap of a recorded range grows it in place
when the pages after it are free, else (MAYMOVE, FIXED) maps the file anew
at the new length and unmaps the old range. munmap, MAP_FIXED over it and
shrinking trim the records; a fork child drops them (Mach rights are not
inherited: its inherited mappings keep the old behaviour).
Test: tests/elf/shm_mremap.c (SHM_MREMAP in tests/elf/run.sh), a
compositor/client pattern with two processes:
  HEAD runtime: [lxrt] mremap: file-backed range ...: not supported yet
                MAL maymove  Cannot allocate memory   == shm mremap: 6 mal
  now, 16 KiB and 4 KiB guest pages:
    ok  maymove  64 KiB -> 1 MiB, old bytes kept
    ok  file     a store past the old end is in the file, and pwrite shows in the mapping
    ok  peer     another process's stores past the old end seen through the grown mapping, and ours in its
    ok  inplace  64 -> 192 KiB at the same address, file-backed past the old end
    ok  shrink   1 MiB -> 128 KiB in place, then back to 1 MiB with the file's bytes

R4  A raw client, and the trampoline
------------------------------------
tests/android/wl_shm_client.c (new): a Wayland client with no library at
all (raw syscalls, the wire protocol by hand), so one source builds for
aarch64 and x86-64: memfd_create, ftruncate, mmap MAP_SHARED, wl_shm pool
sent with SCM_RIGHTS, two buffers, xdg_toplevel, frame callbacks; four
quadrants 0xff2080c0 0xffc04020 0xff20c040 0xffe0e0e0 and a black band
that moves a row per frame.
First runs (aarch64): "== wl_shm_client: FAIL sendmsg (-90)" at different
points in different runs (after create_pool, or at the first attach);
Weston saw the client close. Traced:
  [lxrt] syscall 211 -> 16          (create_pool, with the fd)
  [lxrt] syscall 211 -> -90         (the next sendmsg)
  with a debug print in lxrt_sendmsg: errno 40 (Darwin EMSGSIZE) iovlen 0
The msghdr the client built had msg_iovlen 0. The compiler built it from a
16-byte constant {iovlen 1, control 0} kept in q2 across several inline
`svc`s (llvm-objdump: `ldr q2, [sp, #0x90]` once, `stur q2, [x9, #0x18]`
at each send). A Linux syscall preserves every vector register; lxrun's
trampoline saved x0-x30 only, and the dispatcher (Darwin C, libsystem's
memcpy/memset) clobbered q2. A debug build that happened not to keep it in
a register ran fine (59.2 fps).
The same holds for the condition flags: tests/elf/simd_syscall.c's counted
loop (subs; svc; b.ne) ran a fraction of its iterations, and its own
verdict counter, computed from flags across a write(), printed MAL and
counted ok.
Fix (runtime/trampoline.S): the trampoline saves q0-q31 (st1, 512 bytes),
FPSR and NZCV above the general-purpose block and restores them after the
dispatcher (FPSR written back only if it changed). The frame is 784 bytes
instead of 256; struct lxrt_regs (the dispatcher's argument, clone's
register file) is unchanged at its base. rt_sigreturn does not return
through the trampoline (lxrt_restore_regs), so it is unaffected. FPCR is
not saved (nothing in the runtime changes it). (A scripted rewrite of the
stp/ldp pairs into st1/ld1 also deleted lxrt_restore_regs' 16 vector
loads, the sigreturn path; the diff review caught it before the commit,
they are back byte for byte as in HEAD, and the final checks below were
run again on the corrected build.)
Test: tests/elf/simd_syscall.c (SIMD_SYSCALL in tests/elf/run.sh):
  HEAD runtime:  MAL vregs (round 0, v0), ok fpsr, MAL nzcv
  now:           ok vregs: v0-v31 unchanged across 2000 syscall rounds
                 (openat/read/close/getpid), ok fpsr, ok nzcv (all 16)
Cost, getpid round trip (simd_syscall's counted loop, 200,000 calls, median
of 10 runs, alternating binaries):
  first set:   old trampoline 18.2 ns, new 26.5 ns
  second set:  old 18.8 ns, vectors only 24.1, flags only 23.6, both 23.5
The vector block alone and the flags alone cost about the same, so most of
the price is the larger frame (and the longer trampoline), not the stores;
an unconditional `msr fpsr` and 16 stp-q pairs instead of st1 measured the
same. A null syscall is 25-45% dearer; one that does work (openat, read,
a binder call at 36-55 us) is not measurably so.
Who could have been hit before: code that keeps a value in a vector
register or in the flags across an inline syscall. glibc's syscall
wrappers are functions (callers treat v0-v7/v16-v31 and the flags as
clobbered), but INTERNAL_SYSCALL inside larger functions and freestanding
code are not; no earlier failure is attributed to it (UNKNOWN).

R10 Walls and loose ends, as found
----------------------------------
- Input: hwcomposer.waydroid writes pointer/keyboard events into FIFOs for
  Android's EventHub. The runtime maps /dev/input to one host directory for
  all guests (/tmp/lxrt-input, runtime/evdev.c, steamarm-inputd's nodes),
  so the FIFOs land there; they have no reader without InputFlinger
  (system_server). scripts/run-android-display.sh stop removes them when no
  composer runs. Per-root /dev/input for these FIFOs, next to inputd's
  nodes, is needed before input works.
- No init: bootanimation had to be started by hand (ctl.start refused), and
  nothing sets service.bootanim.exit (no system_server): the animation
  loops until stopped.
- Weston's log attributed a client connection to the pid of an unrelated
  FEXServer (the other session's): the runtime's SO_PEERCRED answer comes
  from a table keyed by socket that can hold a stale sender; only Weston's
  log line is affected here (not investigated further).
- weston-terminal: no /dev/ptmx (R3).
- Everything is CPU: four passes over each frame (SurfaceFlinger's GLES
  composition, the composer's copy, Weston's pixman composite, the X
  server's copy to the window).
