  Symptom (MEASURED, twice): the i386 client segfaulted 3-4 min after start,
  always on a return from a long blocking syscall -- glib's
  g_main_context_poll returning from poll(), and ld-linux.so.2's
  _dl_sysinfo_int80 (`int $0x80; ret`). Host pc was garbage
  (0x7000038000 = G2H(0), or 0x7ef63063f020), reached from JIT code with
  the popped call-ret entry "matching" the guest return address.
  Ruled out by instrumentation: a temporary FEX check that every host code
  pointer handed out by the L1/L2/L3 lookup caches and by the exit linker
  lies in a live code buffer never fired before the crash.
  Cause (VERIFIED IN SOURCE + MEASURED): FEX's per-thread call-ret stack has
  4 KiB (FEX_PAGE_SIZE) guard pages. On 16 KiB host pages the guard shares
  its host page with the stack itself, the page is read/write, and the
  guard never faults. Unbalanced call/ret streams (every lazy PLT bind
  returns through `ret` without a `call`; `call; pop` PIC idioms push
  without popping) drift the stack pointer past either end into whatever
  is mapped next -- typically another thread's call-ret stack -- instead of
  faulting and being reset. New probe tests/elf/i386_callret.c (3 threads,
  400k unmatched rets then 400k unmatched calls each): guard faults taken
  with the old FEX 0 (2 SIGBUS total, both unrelated), with the fix 6
  (2 + 6 = 8), one per thread per direction, as on Linux.
  Fix (FEX patch, minimal): CALLRET_GUARD_SIZE = 16 KiB on each side
  (InternalThreadState.h, ThreadManager.h/.cpp). The probe passes either
  way (the corruption needs a matching neighbour entry); the guard-fault
  count is the check.

M6 (2026-09-27) -- the runtime's vDSO
  runtime/vdso/vdso.c (+ vdso.lds) is a Linux aarch64 shared object with
  __kernel_clock_gettime / __kernel_gettimeofday / __kernel_clock_getres
  (version LINUX_2.6.39, no relocations, no x18), embedded in lxrun
  (vdso_blob.S) and mapped per process by runtime/vdso_map.c below a 16 KiB
  data page; AT_SYSINFO_EHDR points at it. MONOTONIC/RAW/COARSE are read in
  user space exactly as Darwin's mach_absolute_time does it -- the commpage
  (0xFFFFFC088 offset, 0xFFFFFC090 counter type: CNTVCT / CNTVCTSS /
  ACNTVCT) -- scaled by ticks*mult>>32; REALTIME = that + an offset a host
  thread refreshes every 250 ms (seqlock; restarted after fork). Other clocks
  and a tz argument take the syscall. The runtime's own MONOTONIC
  (lxrt_guest_clock_ns) is now the same integer formula, so futex/timerfd
  deadlines agree with vDSO reads to the nanosecond.
  Note (MEASURED): raw `mrs cntvct_el0` in user space does NOT equal
  mach_absolute_time on macOS 27 (different base, reports 1 GHz, ~11.5 ns
  per read -- apparently emulated); only the commpage-selected register is.
  MEASURED (tests/elf/vdso_clock.c, glibc aarch64): vDSO present,
