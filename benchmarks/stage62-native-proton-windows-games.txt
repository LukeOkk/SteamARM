Stage 62 -- Windows games on the native ARM64 Proton path (FINAL FANTASY VII REMAKE)
====================================================================================

Goal (the user, 2026-10-07): every Windows game through the architecture of the
Steam Frame -- Wine, wineserver, DXVK / vkd3d-proton native ARM64 (ARM64EC),
FEX translating only the game's x86-64 code inside Wine -- with Steam's own
redistributable handling (its install scripts, Steamworks Common
Redistributables, Proton's built-in replacements) working. Test title: FINAL
FANTASY VII REMAKE INTERGRADE (app 1462040, Unreal Engine 4.18, Direct3D 12
only, 95 GB), started through "SteamARM: Proton ARM64 nativo"
(tools/steamarm-native-proton) the way the client starts a tool (its reaper,
STEAM_COMPAT_* environment, the client's own LXRT_*/STEAMARM_* settings), with
a test prefix (compatdata/1462040-native) so the player's saves are not
touched. M4, 16 GB, macOS 27.

Everything below was MEASURED unless marked otherwise. Fast checks kept for the
future (scratch, not shipped -- they use the game's own DLL): a Windows x64
program that round-trips 4 KiB to 3 MiB through the game's
oo2core_7_win64.dll (Oodle Kraken/Mermaid/Selkie/Leviathan), an x86-64
instruction-conformance probe (per-group checksums, compared with the x86
Proton path as reference), and a reader of
HKLM\HARDWARE\DESCRIPTION\System\CentralProcessor\N "CP xxxx".

1. A prefix made by another tool: drive links pointing at host paths
   ---------------------------------------------------------------------
   The game's prefix had been created in October by a tool running in the
   ARM64 root outside any container. There the runtime stores an absolute
   symlink target as its host path (runtime/dispatch.c symlinkat), so
   dosdevices/z: was "/tmp/lxrt-arm64root/" and s: a host path too. Inside the
   x86 tool's container neither resolves, Wine found no drive for the game's
   path, passed "\\?\unix\..." to the game's launcher, and the launcher said
   "Couldn't start ... ff7remake_.exe ... CreateProcess() returned 2".
   Removing the two links made Proton recreate them (inside the container,
   as guest paths) and the game's real executable started. Not changed in
   the tools yet: a prefix is made by one tool and should stay with it.

2. The runtime rewrote words inside .NET assemblies (Wine Mono broke)
   ------------------------------------------------------------------
   Wine ARM64 marks the sections of every PE image executable as Windows
   does, IL-only .NET assemblies included, and the runtime scanned them for
   svc / TLS / system-register words when they became executable: it
   "rewrote" two system-register reads inside wine-mono's mscorlib.dll -- its
   metadata -- and Mono stopped at "Runtime critical type System.Int16 not
   found". No .NET program ran, Proton's own prefix setup included.
   runtime/rewrite.c now never rewrites a word of a PE image outside the
   image's aarch64 code windows (pefile.c: the CHPE code map's ARM64 and
   ARM64EC ranges, or the executable sections of a plain ARM64 image): the x64
   side of ARM64X DLLs, pure x64 images and IL are left alone for every kind
   of site. pefile.c also recognises PE32 images (mscorlib is one), parses an
   image found at a 64 KiB boundary inside a scanned range, and forgets an
   image a fixed mapping replaces (a view Wine released and reused).
   After: Mono's programs exit 0 (CorExitProcess(0)).

3. Wine read no CPU identity: HWCAP_CPUID
   ---------------------------------------
   FEX's ARM64EC JIT reads the host's ID registers from the registry values
   Wine writes (CP 4000 MIDR, CP 4020 PFR0, CP 4030 ISAR0, CP 5801 CTR ...).
   Wine writes them only when AT_HWCAP has HWCAP_CPUID ("the kernel emulates
   mrs of the ID registers"), which the runtime left out because, before it
   rewrote those reads into constants (sysreg.c), glibc's start-up took
   SIGILL on them. Every value was missing (RegGetValue: 2), FEX took the M4
   for an ARMv8.0 core without CRC32, and the x86 crc32 instruction raised
   EXCEPTION_ILLEGAL_INSTRUCTION. Now:
   - AT_HWCAP has HWCAP_CPUID, /proc/cpuinfo says "cpuid", /proc/self/auxv
     agrees -- for every program except FEX itself (the x86 path's FEX on
     Linux): told it may read the ID registers, it switched its x86
     memory-order emulation to the RCpc/LSE2 forms, and in the first
     Counter-Strike 2 runs the median frame went from 7.2 ms to 8.9-10.3 ms.
     Alternating runs later put the installed 0.3.57 runtime at 91-138 fps
     and this one at 95-125 on the same scene, so most of that was this
     benchmark's spread, but FEX on Linux needs nothing from the bit and now
     sees AT_HWCAP exactly as before. LXRT_NO_HWCAP_CPUID=1: the bit for
     nobody; LXRT_HWCAP_CPUID=1: for everybody;
   - an ID-register or CTR_EL0 read the rewriter never saw is emulated from
     SIGILL with the same synthetic value (signal.c);
   - /sys/devices/system/cpu/cpuN/regs/identification/midr_el1 exists
     (sysfs.c), which Wine reads for CP 4000.
   After: CP 4000 = 0x610f0301, CP 4020/4030/5801 present; the conformance
   probe's 30 groups (BMI1/2, ADX, CRC32, SSE4, AVX2, x87-free FP, flags,
   division ...) give the x86 path's checksums bit for bit.
   With the real features FEX emits RCpc loads (LDAPR/LDAPUR) for x86 loads
   under TSO; runtime/lowpage.c (the KUSER_SHARED_DATA page at 0x7ffe0000)
   now carries those forms out too ("lowpage: cannot carry out 194000c6").

4. The root cause of the Oodle crash: sigcontext.__reserved at 280
   ---------------------------------------------------------------
   Every Unreal Engine 4/5 game decompresses its data with Oodle. The game
   died in oo2core_7_win64.dll ("page fault on read access to
   FFFFFFFFFFFFFFFD" at oo2core+0x1C04), deterministically, with both FEX
   builds Valve ships (Proton Experimental's and Proton 11.0's), and the
   probe reproduced it in seconds: 4 KiB Kraken/Mermaid/Leviathan blocks
   failed, larger ones passed. At the fault RAX, RDI and XMM2 held host
   values (XMM2 = the stack pointer at the last signal). The chain: FEX's
   TSO load of an unaligned value took an alignment fault, Wine ARM64
   dispatched it to FEX (which emulates the access) and resumed through
   NtContinue -- a SIGUSR2 to itself whose handler writes the full context
   into the signal frame. Linux's struct sigcontext has
   `__u8 __reserved[4096] __attribute__((__aligned__(16)))`, at offset 288;
   the runtime's had it at 280. The runtime wrote and read its own frames
   consistently, so native programs that ignore the FP/SIMD record never
   noticed; Wine found no FPSIMD_MAGIC there and put garbage back into the
   vector registers. Fixed in runtime/signal.c (pad + _Static_assert), and
   the frame now carries Linux's esr_context record after the FP/SIMD one
   for memory faults, so Wine can tell a store from a load (it reported a
   store as "read access").
   After: the Oodle probe passes all 16 cases; the game passes Oodle and
   creates its Direct3D 12 device.

5. membarrier answered "nothing supported"
   ----------------------------------------
   MEMBARRIER_CMD_QUERY returned 0, so Wine ARM64 logged "membarrier not
   supported for NtFlushProcessWriteBuffers" and fell back to interrupting
   every thread. Now QUERY returns GLOBAL | PRIVATE_EXPEDITED (+SYNC_CORE) and
   their REGISTER commands, and the barrier is the one .NET uses on macOS:
   thread_get_register_pointer_values on every thread of the task.

6. Loading took forever: four costs in the runtime's memory calls
   --------------------------------------------------------------
   With 4 KiB guest pages (the client's setting, inherited by its games) a
   game's 4 KiB mappings go through the sub-page table. While the game
   loaded, its main thread lived in the runtime:
   - the sub-page table was a list walked whole on every lookup and update
     (record() restarted its merge loop after each merge); now a sorted
     interval list with binary search (runtime/subpage.c);
   - 1.37 million failing mmaps a minute: Wine looked for room below 4 GiB
     before every allocation -- some 80 probes each -- and the runtime said
     EEXIST ("busy, try the next address") for __PAGEZERO, which exists and
     can never be mapped. ENOMEM now, below 4 GiB, which ends each such range
     at its first probe (and the sub-page check is skipped there);
   - Xalia, Proton's gamepad navigation of launchers (a Steam Deck feature),
     mapped and unmapped a section in a loop and walked every window tree:
     254000 map_view requests to wineserver while the game loaded, the game
     waiting behind them. Both SteamARM tools now default to
     PROTON_USE_XALIA=0 (the game's launch options can set 1);
   - the x18 virtualisation itself: the kernel keeps x18 for a process lxrun
     was exec'd as, and Wine expects exactly that (its Linux side may use x18
     as a temporary, the TEB is restored on every return to Windows code). The
     native tool now runs Wine with LXRT_NO_X18=1: no trampolines in Wine's PE
     code or in FEX's JIT output. The game reached the same point in 5 s
     instead of 3 min. STEAMARM_X18_VIRT=1 restores the old behaviour.
   Also: a partial MAP_FIXED_NOREPLACE reservation now records its host
   page's rest as a placeholder, a sub-page host page left with no record
   goes to PROT_NONE, and a fixed mapping of whole host pages drops the
   sub-page records under it -- so Wine's shared sections (reserved, then a
   file view mapped over the reservation) are shared mappings more often
   instead of private copies. Not finished: a view re-mapped at an address
   whose host page still holds an older mapping's records is still a copy
   (Wine re-maps its session shared memory there; each copy is a fresh
   snapshot, so it works, slowly).

   Steam's install-script evaluator (legacycompat/iscriptevaluator.exe) is a

   Wine's WoW64 needs the low 4 GiB, which macOS reserves (__PAGEZERO). That

9. Geometry shaders in KosmicKrisp
   --------------------------------
   patches/kosmickrisp-27: emulation with Mesa's poly library as Honeykrisp
   does it. For a VS+GS+FS pipeline the vertex shader becomes a compute
   kernel (as before tessellation), poly_nir_lower_gs splits the geometry
   shader into a compute kernel that writes the emitted vertices and a
   "rasterization" vertex shader that reads them, and that one is paired
   with the fragment shader in the Metal render pipeline. Each draw uploads
   poly's vertex and geometry parameters, dispatches the two kernels before
   the pass and draws the rasterization shader, indexed by poly's static or
   dynamic index buffer; indirect draws set their grids on the GPU
   (libkk_gs_setup_indirect); primitive restart is unrolled first. Two
   things the first version (written with codex) lacked: poly's shaders
   carry local variables, which nothing lowered ("Unknown intrinsic
   load_deref" in the MSL), and the rasterization shader's load_clip_z_coeff
   appears after the descriptor pass had run. Not supported: tessellation
   together with a geometry shader, transform feedback from one, geometry
   pipeline statistics. KK_GEOMETRY_SHADER=0: no geometry shaders, as before.

   Check: tests/kk/vk_geometry.c draws seven scenes with KosmicKrisp and with
   llvmpipe and compares them pixel by pixel (64x64): pass-through, points
   to quads, EndPrimitive with a varying count, gl_Layer from two
   invocations into a 2-layer image, vkCmdDrawIndirect, an indexed strip
   with restart, a strip with back faces culled. Six are identical; the
   restart scene differs on 30 pixels where overlapping triangles meet
   (coverage identical, also with culling: the winding is right; which
   triangle ends on top differs).

   Counter-Strike 2 (no geometry shaders) with and without the patch: see 12.

   FINAL FANTASY VII REMAKE: the pipelines build, no error box, and the game
   draws: "Got 4 swapchain images" 30 s after start, then 60 presents per
   2 s (30 fps, the game's own limit on its opening screens) for minutes,
   no errors, 55 % CPU, 1.1 GB.

13. A guard page FEX relies on (runtime)
    ------------------------------------
    The first failure of Minecraft Dungeons II on the native path: "Exception
    frame is not in stack limits => unable to dispatch exception" after an
    access violation at 0x7FFFFC72FFF0 on every x86 call instruction. FEX's
    ARM64EC JIT keeps a call-return stack (VirtualAlloc: 4 MiB with a 4 KiB
    no-access page on either side) and resets it when a fault lands in that
    range -- an unbalanced call/ret stream like the game's obfuscated code
    walks it off the bottom. With 4 KiB guest pages on 16 KiB host pages the
    bottom guard shares its host page with 12 KiB of the stack, the host
    page is read-write (the union, runtime/subpage.c), so the overflow went
    through the guard and faulted 16 bytes below the reservation, outside
    FEX's range ("Passing through exception"). The runtime now reports a
    fault within 64 bytes below a host page whose bottom guest page is such
    a lost guard inside that guard, where it happens with 4 KiB pages:
    "Call-ret stack inbalance" in FEX's log, and the game went on.
    tests/elf/lost_guard.c checks it (the same layout, three rounds).
    The same test found that a guest handling SIGSEGV but not SIGBUS died
    on a store into a PROT_NONE reservation: Darwin raises SIGBUS there,
    the runtime turned only "withheld" protections into SIGSEGV, and a
    host SIGBUS without a guest SIGBUS handler went to the fatal report.
    Now PROT_NONE is SIGSEGV/SEGV_ACCERR as on Linux, and installing a
    SIGSEGV handler routes the host's SIGBUS through the same conversion.
    tests/elf: 114 passed.

14. Every Steam launch on the native path: "undefined symbol: setsid"
    -----------------------------------------------------------------
    Launched from the Steam client (not from the test harness), every game on
    "SteamARM: Proton ARM64 nativo" stopped at once: wineserver died with
    "symbol lookup error: .../wineserver: undefined symbol: setsid, version
    GLIBC_2.17" and the game said "Descriptor invalido". The root's libc
    exports setsid@@GLIBC_2.17 and wineserver loaded that libc
    (LD_DEBUG=libs,versions). Found with four subagents in parallel (the
    reproduction without the Steam GUI, 5/5 and 50/50):
    - the client preloads the Steam overlay for games, and the arm64 one
      (<Steam>/ubuntu12_64/../steamrtarm64/gameoverlayrenderer.so) loads
      silently; the harness had no loadable preload, which is why it never
      failed;
    - the tool runs everything with LXRT_NO_X18=1 (no x18 virtualisation,
      for Wine's PE code and FEX's ARM64EC JIT, which keep the TEB there);
    - wineserver daemonises with fork; a fork child loses the kernel's x18
      preservation and its first page faults (every inherited page faults
      once in the child on macOS 27) zero the register;
    - the Steam Frame root's ld.so keeps the lookup scope length in w18 in
      do_lookup_x (ldr w18,[x5,#8] ... cmp x18,x4): with x18 zeroed, the
      child's first lazy binding, setsid, stopped after the overlay and never
      reached libc (LD_DEBUG=symbols: "lookup in file=wineserver",
      "lookup in file=.../gameoverlayrenderer.so", then the error).
    Fix: the runtime applies LXRT_NO_X18 to Wine's loaders only (wine,
    wine64, wine-preloader, wine64-preloader: the processes that run PE
    code); wineserver, python3 and the other plain ELF programs under the
    tool keep the virtualised x18 (runtime/wxsplit.c lxrt_no_x18).
    Measured: the daemon loop 0/5 failures (5/5 with the old runtime); the
    client's whole chain (steam-launch-wrapper, pw-audio-namespace, reaper,
    the tool, proton, wine, wineserver) with the overlay preloaded runs;
    FINAL FANTASY VII REMAKE with the client's three overlay preloads reaches
    its swapchain in 35 s. tests/elf/fork_lazy_bind.c checks it against the
    Steam Frame root's ld.so when that root is present (old runtime 0/20
    children, new 20/20).

15. Minecraft Dungeons II: from "exit code 300" to the menu
    -------------------------------------------------------
    The game closed itself 74 s after start with exit code 300, before any
    GDK or Direct3D DLL. A panel of four subagents concluded "the protection's
    watchdog fires because FEX ARM64EC runs its self-modifying code 20-50x too
    slowly", and an AoE IV-style FEX build (FEX 7d3090f with that project's
    patches 0004-0016, ~/SteamARM-build/FEX-arm64ec) changed nothing. Sampling
    the process showed the opposite: 15 s of CPU, then 60 s with every thread
    waiting. Five runtime problems, found one after the other with
    WINEDEBUG=+server and LXRT_TRACE_MATCH:
    a. NETLINK_ROUTE. The protection fingerprints the machine (MachineGuid,
       DigitalProductId, the adapter list). Its GetAdaptersInfo-style NSI
       enumeration never returned: glibc's if_nameindex() needs a
       NETLINK_ROUTE socket, the runtime answered EAFNOSUPPORT, and Wine's
       nsiproxy.sys (update_if_table) dereferences the NULL it gets -- a
       SIGSEGV at address 0 inside winedevice, while holding its interface
       list lock. Every later enumeration in the prefix waited on that lock
       for good. The runtime now answers rtnetlink dumps (RTM_GETLINK,
       RTM_GETADDR) from Darwin's getifaddrs, the SIOCGIF* ioctls, and
       /proc/net/{route,ipv6_route,arp,dev} from the routing table
       (runtime/netif.c; tests/elf/netif.c). The next NSI request, the IPv4
       forward table, needed /proc/net/route: without it the answer was
       STATUS_NOT_SUPPORTED and the game exited on the spot.
    b. Shared section views. The main thread then maps an 8 KiB anonymous
       section, writes through the view and maps it again until the write
       shows -- 1.4 million times in 190 s. Wine releases a view with a
       PROT_NONE mapping over exactly its length; the runtime adopted the
       rest of the 16 KiB host page (the shared mapping's rounded-up tail)
       as live memory, and from then on every view at that address was a
       PRIVATE copy ("MAP_SHARED ... mapped as a PRIVATE copy"). The tail is
       now noted as free (subpage.c g_tails; tests/elf/shared_view_cycle.c,
       which the old runtime fails at the fourth view).
    c. PE discovery. Every executable flip of anonymous memory asked
       pefile.c's discover() whether the page lies in a PE image: a walk of
       up to 1024 mach_vm_reads with a 256-entry negative cache. FEX
       ARM64EC's code buffer is ordinary RWX memory to Wine, so that is
       every block FEX compiles, with thousands of 64 KiB chunks: nearly
       every flip missed, 2 ms each under the W^X lock. Now a 16384-entry
       hash set, and the walk stops at a chunk already known to be empty.
    d. ORC's dual mapping. Past the protection, the intro video starts
       GStreamer; its ORC JIT maps its code file twice (read-write and
       read-execute, MAP_SHARED) and runs from the second. The runtime made
       the executable view a private snapshot of the still-empty file, and
       the first ORC function was zeros (SIGILL, insn 00000000 at a page
       start, lr in GStreamer). Darwin refuses mmap with PROT_EXEC on a
       shared file mapping (EPERM) but lets mprotect add execute to one: the
       view is mapped shared and readable, then made executable
       (dispatch.c do_mmap; tests/elf/dual_map_jit.c).
    e. wined3d's OpenGL backend. After its first frame the game stopped
       presenting: the main thread (dxcore -> wined3d -> opengl32.so, DXCore
       asks wined3d for the adapter list even under vkd3d-proton) and
       vkd3d-proton's present thread (winevulkan -> win32u -> libX11) each
       waited on a lock the other held. The native tool sets
       WINE_D3D_CONFIG=renderer=vulkan by default: no GLX at all.
    Also: a low-page fault (KUSER_SHARED_DATA, emulated) that arrived with
    the thread already redirected into Darwin's signal trampoline -- the
    game's integrity scanner suspends every thread over and over, and Wine
    suspends with SIGUSR1 -- went to the guest, and the game died once in a
    7-minute run. Such a fault is now let through: the trampoline runs, and
    its sigreturn retries the access with its own pc (lowpage.c). The
    runtime's fault report keeps 16 distinct pcs per signal, with the
    instruction word (signal.c): the first eight were all FEX's own trap.
    The community xgameruntime.dll/XCurl.dll stand-ins are not needed (the
    game's MicrosoftGame.config does not require Xbox Live; 1.1.2.0 runs on
    stock Proton on the Deck) and were taken out again. No Microsoft sign-in.
    f. Nested signal frames. Past the menu the game still died after two to
       five minutes, each time differently (D3D12 E_INVALIDARG, an x64 return
       into ASCII bytes -- rip 0x7473694C6E6967, "ginList" --, a stack
       overflow, a silent exit): memory corruption. Its integrity scanner
       suspends, reads and resumes every thread of the game, over and over;
       tests/win/suspend_storm.c does the same to computing threads, and

    h. D3D12 tight alignment. The fatal "D3D12Resources.cpp:1042 ... E_INVALIDARG"
       came with vkd3d-proton's "d3d12_resource_create_placed: Heap offset
       0xfa8000 not a multiple of resource alignment 0x10000". vkd3d-proton
       reports D3D12's tight alignment (tier 1) whenever bufferImageGranularity
       is 4 KiB or less; GetResourceAllocationInfo then answers a texture with
       the Vulkan alignment (KosmicKrisp: 16 KiB for optimal images, 128 bytes
       for small ones -- before and after creation alike, 756 images
       checked), but CreatePlacedResource keeps D3D12's 64 KiB unless the
       driver has VK_MESA_image_alignment_control. Unreal Engine 5.6 uses tight
       alignment when it is offered. A bufferImageGranularity of 16 KiB from the
       Vulkan shim (vkd3d-proton's tier test) did not stop it. Logging the
       shim's answers showed why no D3D12-like rule did: KosmicKrisp asks only
       128 bytes of most optimal images, a 64 KiB texture included. The shim
       now answers 64 KiB for any image over 4 KiB and 4 KiB below
       (shim/features.c; images created as render targets, depth or
       multisampled are remembered for the queries that carry only a handle;
       LXRT_VK_IMAGE_ALIGN=0 turns it off): a stricter alignment is always a
       valid Vulkan answer, and vkd3d-proton pads a "small resource" the app
       wants at 4 KiB. Refused placements went from every run to some runs --
       they depend on thread timing and never showed with LXRT_VK_DEBUG's
       logging on. FF7R (30 fps) and Schedule I (89 fps, DXVK) unchanged.
    i. The refused placements, properly. An instrumented build of vkd3d-proton

       alignment (h) would push textures over their neighbours once
       vkd3d-proton aligns them up, so it is off by default
       (LXRT_VK_IMAGE_ALIGN=1, LXRT_VK_GRANULARITY=<bytes>). FF7R 30 fps,
       Schedule I 89 fps with this build.

       RtlUnicodeStringToAnsiString(..., TRUE) -- an allocation from the

    m. /proc/self/task/<tid>/stat did not exist: the runtime generated comm
       and status only. Wine's GetThreadTimes reads it for every thread but
       the caller, so every other thread had used no CPU, ever. It is now
       generated with the thread's own CPU times (thread_info of its Mach
       thread), for the thread asked about only: rewriting every thread's
       files on each lookup took a sixth of the protection thread's time,
       which asks several thousand times a second (tests/elf/task_stat.c).
       The process-wide fields are refreshed at most once a second: walking
       every VM region per read slowed the game's start fivefold.
    n. The ~125 s death, traced with FEX's log extended (the bytes of every
       guest exception, its RSP, a ring of the last contexts per thread):
       it is time, not frames (at 20 fps: 2029 frames, 123 s). The game's
       code is encrypted on disk and decrypted in place; its protection runs
       a virtual machine whose instructions are invalid opcodes (16, d5, 06,
       27, 1f, 0e, 1e, 3f, 37, 60, ea, d4, 9a, 07, 17 -- about 5,000 traps a
       second, ~250 us each here against a few us on Windows), dispatched by
       a vectored handler. About two minutes in, two of its threads leave the
       dispatcher (a trap at 0x148BF770B) for code that is still encrypted;
       the handler declines it, Wine's unwinder takes a garbage PC to
       RtlIsEcCode, which indexes the EC bitmap without a bound, faults, and
       recurses to a stack overflow (1,672 nested faults); UE's crash handler
       then suspends every thread for a minidump and the process dies with
       a corrupted stack. The thread stacks do not leak (RSP stable over
       530,000 traps), the clocks agree (rdtsc 1536 MHz = CPUID 15h =
       ~MHz), and the window between decoding and write-protecting a code
       page in FEX (FEXCore CompileBlock) is not hit (checked: 0 changed
       blocks). Still open. The deadline is about 140 s after the process
       starts, whatever the trap speed: a protection thread (entry
       0x148B2B894) waits 139.94 s on an event of its own that nothing
       signals, wakes on the timeout, and within a second or two the VM
       threads leave the dispatcher for still-encrypted code. Either the
       success path needs another protection thread to signal that event
       first, or the thread re-keys the VM when it wakes -- microseconds on
       Windows, seconds of traps here, a window the other VM threads run
       into. FEX's experimental build that hides its SMC write protection
       from NtQueryVirtualMemory (benchmarks/stage62 h, ~/SteamARM-build/
       FEX-arm64ec) dies earlier of a fault loop inside FEX.

    p. The "stop at ~680 frames" was the harness: LXRT_VK_FRAMETIMES appends
       in 4 KiB pieces (about 680 lines) and the watchdog called 20 s without
       growth a stall, while the shim's present timing showed ~38 fps all
       along (LXRT_VK_FRAMETIMES_SYNC=1 writes per present). Without
       PROTON_LOG the game runs like with it and dies at the same ~140 s.
       Found and fixed on the way, none of which moves the ~140 s death:
       - EFlags PF and AF did not survive an exception: ARM64EC's context
         has only NZCV, ntdll dropped the rest and FEX resumed with PF=AF=1
         whatever the code had (tests/win/veh_flags.c: 4 of 4 wrong). Now
         patches/wine-ntdll (from GameNative/proton-wine 47; built by
         scripts/build-wine-ntdll.sh from the Wine source of this Proton
         build) carries them in RES0 cpsr bits 26/27 and FEX's patch 0008
         reads them back: 0 of 4 wrong.
       - FEX patches 0002-0012, Dmage22/FEX-D2's ARM64EC fixes for Arxan-
         protected Blizzard loaders, and 0014: a guest exception the JIT
         raises calls the frontend directly instead of a host trap (+8 %
         traps).
       - FEX's call-return stack ran past its TOP guard page: the VEH's
         emulated pushes and pops are an unbalanced call/ret stream, and the
         guard plus the free pages after the reservation share the stack's
         last 16 KiB host page, so the pop faulted a host page further,
         outside FEX's range; the thread then retried that fault 10,000
         times and died, or took the slow way out. runtime/subpage.c reports
         such a fault in the guard (tests/elf/lost_guard.c, top case).
         tests/win/veh_traps.c: 503,760 -> 1,292,695 traps in 40 s (3
         threads; ~93 us a trap).
       - FEX's DiskCache bucket is keyed on its format version and the host
         only: builds with another CpuStateFrame layout ran each other's
         cached code and crashed at once. Patch 0015 gives SteamARM's FEX a
         format version of its own (Proton's FEX shares the Steam shader
         cache directory).
    q. The ~140 s death was two independent killers, each due at about the
       same wall time (found by a second investigation; a 2x2 run matrix):
       - Self-modifying code FEX did not see. The protector writes a fresh
         stub into a 16 MiB ring (0x14DE00000-0x14EE07000) before each run
         of it. FEX write-protects each 4 KiB guest page of code it has
         translated, but a 16 KiB host page carries the union of its four
         guest pages: a store into a protected page whose host page also
         held a writable one went through without a fault, and once the
         ring wrapped FEX ran last lap's translations until it jumped into
         a slot not yet written (57 % of the SMC faults FEX did see were in
         the last 4 KiB of a host page). Now FEX tracks SMC in 16 KiB blocks
         (patch 0016; STEAMARM_FEX_SMC_BLOCK=4096 restores FEX's own), and
         the runtime hands a store into a guest page the guest did not make
         writable to the guest as a fault instead of flipping the split host
         page to read-write (runtime/subpage.c).
       - The anti-tamper's watchdogs: protection threads (entries 0x148B2B894,
         0x148B3DDBC) wait on events of their own with timeouts of 90, 139.94,
         162.7, 196 and 300 s, and each expiry starts the tear-down. Under
         emulation whatever signals them in time does not finish. With only
         the 140 s one neutralized the game died at 166 s (the next one).
         patches/wine-ntdll 0002: with STEAMARM_NO_LONG_WAIT_TIMEOUTS=1 a
         wait whose timeout is 60-400 s ahead never expires; the native tool
         sets it for app 1912410 only.
