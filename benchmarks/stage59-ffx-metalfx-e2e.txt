What was fixed before measuring (review of commits 77d3a8b, 4e3f811):

- Every call into the game's own DLL (forward_create, forward_query, the
  fallback's link_chain) goes without an ffxOverrideVersion naming THIS
  DLL's version id. [F] AMD's GetffxProvider (ffx_provider.cpp, SDK 1.1.4
  and 2.3.0 sources) only returns a provider whose id equals the override
  and otherwise none, so ffxCreateContext / ffxQuery answer NO_PROVIDER: a
  game that chose our version (first in the version list) and hit any
  forward path would have lost FSR altogether.
- The backend descriptor type 3 is decoded per SDK generation (build.sh:
  FFX_SDK2=1 for the amd_fidelityfx_upscaler_dx12 / _framegeneration_
  names). [F] SDK 1.1.4 vk/ffx_api_vk.h: 3 = the Vulkan backend; SDK 2.3.0
  dx12/ffx_api_dx12.h: 3 = FFX_API_CREATE_CONTEXT_DESC_TYPE_BACKEND_DX12_
  ALLOCATION_CALLBACKS (five callbacks, 56 bytes), the Vulkan backend
  0x02000003. Allocation-callback descriptors are copied and passed
  through to the game's DLL on every forward and fallback path.
- Jitter phase count: int32(8 * pow(r, 2.0f)). [F] AMD's 1.1.4 DLL imports
  no powf/pow (objdump: MSVC folded it into r * r; identical to r * r in
  the 4 sizes tests/win/d3d12_ffx.c asks); AMD's 2.3.0 upscaler DLL does
  import powf, so the SDK 2.x build calls ucrtbase's powf (the one AMD's
  DLL calls under Wine), r * r only if that cannot be loaded.
- Colour space: FFX_UPSCALE_ENABLE_NON_LINEAR_COLORSPACE at creation and
  FFX_UPSCALE_FLAG_NON_LINEAR_COLOR_SRGB / _PQ at dispatch send the context
  to the game's own upscaler (the channel, shim/mfx_temporal.h v1, has no
  colour-space field; MetalFX takes linear colour) -- at creation the game
  never sees a switch; at dispatch the context is the game's from then on,
  logged once. transparencyAndComposition stands in for the reactive mask
  when the game gives only it; with both, the reactive mask goes and the
  other is dropped (logged once). The reactive-mask generator (0x10006)
  switches the context to the game's upscaler for good (logged).
- No game DLL to fall back to (none loadable, or its context refused) and
  a frame MetalFX does not take (ENCODE refused, or a dispatch known
  beforehand not to fit): the colour input is blitted to the output
  (vkCmdBlitImage, linear filter) in the game's command buffer, between
  image barriers from the layouts vkd3d reports for the resources' D3D12
  states (GetVulkanImageLayout) to TRANSFER_SRC/DST and back. The output
  is never left untouched.
- Harness: tests/win/run_d3d12_ffx.sh writes each invocation's outputs to
  a directory of its own and compares forward against amd only when both
  ran and passed in that invocation; run_ffx_samples.sh appends to
  ffx-e2e-summary.txt with a dated header per invocation and writes each
  variant's own .summary file.

The blit mode's game copy is a stub DLL whose DllMain returns FALSE
(ERROR_DLL_INIT_FAILED 1114 on LoadLibrary); a game directory with no file
at all is not the case, since without a file of that name Wine finds no
builtin to map either [F: the earlier attempt ended in LoadLibraryA
failed: 126]. The blit's RMSE 0.0967 (a bilinear upscale of an input
jittered by up to half a pixel; MetalFX 0.036/0.063, FSR 3.1 0.056/0.061)
sets FFX_BLIT_MAXERR's default at 0.15 [F: a rerun of the blit mode at
15:38 on KosmicKrisp 14db8073ef71 passed with "RMSE 0.0967 (limit
0.150)" for both cases]. The review's earlier failures of
metalfx ("no ENCODE st=OK") and forward ("guest signal 4") did not
reproduce with this DLL [F: the runs above]; their cause is not known [I:
they predate the fixes above and used an unknown KosmicKrisp build].

Reading. [F] Both samples take our version id, every ENCODE is OK, nothing
is refused and nothing falls back; the SDK 2.x sample's creation chain
carries the allocation-callback descriptor and is taken (the earlier
build would have refused it as "two backends"). [F] The sample's own GPU
timer around its upscale dispatch reads 2.7 ms (1.1.4) and 2.4 ms (2.3.0)
with ours against 3.9 and 3.5 ms with AMD's FSR 3.1; frame generation
(AMD's, forwarded) still presents 2.01 frames per benchmark frame in
every run; the frame rate is bound elsewhere (25-26 fps either way). [I]
What that timer covers on our path is the ENCODE command as KosmicKrisp
records it; whether it spans all of MetalFX's work is not established
here. [F] Our frames are softer: the sharpness number is about half of
FSR's (226 vs 497, 246 vs 494) and 9-11% of the pixels differ noticeably
from FSR's; SA_MFXT_SHARPEN is sent (flags 0x66). [I] Whether the driver
applies the sharpening is not shown by these runs.
