Two runtime defects stood between V8 and its code pages; both are fixed:

1. mprotect(RWX) of anonymous memory was granted as read-write (right for x86
   V8 under FEX, whose code the host never executes; wrong for native code).
2. When the guest set SIGSEGV/SIGBUS back to SIG_DFL, the runtime set the
   host disposition to SIG_DFL too, so the runtime's own fault handlers (JIT
   and W^X flips, sub-page flips, privmap copy-on-write) never ran: the
   kernel killed the process on the first such fault. The webhelper's zygote
   does that before it forks renderers. This is why stage 22 E11 found "No
   lxrun report precedes it" for the renderers' SIGBUS.
Fixing 1 alone changed nothing (E1: 2281 renderer launches in 180 s, no
window). 1 + 2 gave the window (E2).

Design (runtime/wxsplit.c)
--------------------------
The task proposed turning the range into MAP_JIT and letting runtime/jit.c's
per-thread switch handle it. Not done, for this reason: jit.c rescans, on a
thread's flip back to execute, only what that thread was told or guessed it
wrote (4 KiB after the first faulting store; note_written(), VERIFIED IN
SOURCE runtime/jit.c). MAP_JIT's write/execute switch is per thread
(UPSTREAM DOCUMENTED, pthread_jit_write_protect_np; MEASURED for this
runtime in stage5-jit.txt): a thread in write mode stores to any MAP_JIT
page without faulting while every thread in execute mode runs the same page
without faulting. V8's background compile and GC threads write code the
main thread runs, and never flip back themselves. So with MAP_JIT an
unpatched JIT's bytes can execute without ever being scanned, which breaks
the rule that no executable page may hold an unvalidated svc.

Instead, a native guest's RWX range of private anonymous memory is recorded
(sorted, merged range table: V8's 256 MiB is one entry; 5000 separate
commits are 5000 entries, no fixed limit) and each 16 KiB host page of it is
either read-write or read-execute, never both:
  - store into a read-execute page -> fault -> the page becomes read-write;
  - instruction fetch from a read-write page -> fault -> the page is made
    READ-ONLY, the RWX guest bytes in it are counted for svc / mrs-msr
    TPIDR_EL0 / mrs CTR_EL0 / ID-register reads (lxrt_rewrite_count, a
    read-only census), rewritten if any (page opened RW for that), counted
    again read-only until clean, then made read-execute and the I-cache
    invalidated.
Page protections are process-wide, so no thread can execute a byte that was
not scanned after its last store, whichever thread stored it. A page nobody
executes stays read-write, which is all the old grant ever gave. Sub-page RWX
commits (4 KiB inside a 16 KiB host page, subpage.c's union split) are
scanned the same way before their host page becomes executable; RX and RW
guest pages sharing that host page are not scanned (code already scanned /
data). Any other protection ends the split for its range (RX goes through
rewrite_and_seal as before, PROT_NONE is PROT_NONE); munmap, MAP_FIXED and
mremap keep the table in step; madvise(DONTNEED) keeps the host protection.
FEX keeps the RW grant: the main program's name decides (FEX, FEX-gb,
FEXInterpreter, FEXLoader; not FEXServer); LXRT_WX_SPLIT=0/1 overrides.
The table's lock is taken with asynchronous signals blocked (a guest handler
runs nested in the host handler and could otherwise wait on its own lock).

x18 in JIT output: the scan does not run the x18 pass (it needs executable-
section windows, which generated code does not have). V8 excludes x18 from
its allocatable registers ("x18 is the platform register and is reserved for
the use of platform ABIs", ALWAYS_ALLOCATABLE_GENERAL_REGISTERS without x18:
UPSTREAM DOCUMENTED, v8 src/codegen/arm64/register-arm64.h, main branch as
fetched 2026-09-29). MEASURED in the renderer (LXRT_WX_STATS=/path logs the
first 64 x18-naming words with 4 words either side): 34 x18-naming words in
scanned pages over 180 s, 8 distinct contexts, every one among words such as
0x0000000b, 0x0000000d, 0x000006c8, 0x00000a88 that are not plausible code
(as instructions they are udf), i.e. V8's code-object metadata tables. E.g.
  a92b0068 0000000b b12c0208 0000000b [b92d0644] 0000000b 000006c8 001b0800
  00000900 01c60a00 0000093c 01e60a00 [b1260a44] 00c6080e 00000a88 00c60800
So: no evidence of x18 in executed V8 code (HYPOTHESIS that there is none,
supported by the source and by these samples; not proven by disassembling
every JIT page).

Still open
----------
1. L2: a webhelper zygote died at start with SIGBUS inside a host memset,
   before the guest had installed any handler (so the runtime's startup
   fault reporter caught it). 1 of 10 launcher cycles, 0 of 7 direct runs;
   the only such line in $STATE/logs. Cause UNKNOWN; whether this stage's
   changes play a part is UNKNOWN. The report now prints the fault address,
   sp and lr for the next occurrence.
2. mmap(RWX) (as opposed to mprotect) by a native guest still becomes
   MAP_JIT with jit.c's switch, whose rescan is exact only for a guest that
   names its ranges (FEX, patched). An unpatched native JIT that maps RWX
   directly gets the weaker scan. V8 does not do this (trace above).
3. /proc/self/maps shows a split range as rw-p or r-xp, not rwxp.
4. A store executed from the host page it writes never makes progress (the
   same limit as tests/elf/run.sh's subpage4k xfail); the runtime says so
   after 1000 repeats (on the renderer's stderr, which nobody reads).
   Whether V8 ever does it is UNKNOWN; the flip counts of E3/E5/E7 (about
   500 each way in 180 s) show no such livelock.
5. A rewritten site in JIT output is a PC-relative branch to a trampoline;
   code that is later copied elsewhere (V8's code-space compaction) carries
   a broken branch. 0 sites were found in V8's output in E3/E5/E7.
6. A system call that writes guest memory (read(2) into a buffer) in a split
   page while it is read-execute would get EFAULT from Darwin, where Linux
   writes; the same holds for MAP_JIT regions. Not measured; not seen.
7. XOpenIM() with LANG=es_MX.UTF-8, steam-runtime-launcher-service, the
   file-backed mremap message, GL on XQuartz: unchanged from stage 22.
