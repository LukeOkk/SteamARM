Stage 61: Counter-Strike 2 stutter at high frame rates (2026-10-06)
===================================================================

The user: "stuttering muy seguido a pesar de altos fps". Dust2 with bots
(+map de_dust2, local), 1920x1080 windowed, textures medium, MSAA 2x,
shaders low, FSR detail 2; M4, 16 GB, macOS 27; SteamARM 0.3.53 + the
fixed shim (stage 60's gen_rebase fix); KosmicKrisp. Frame times from
LXRT_VK_FRAMETIMES (shim/scaler.c), 90-150 s windows after a 75 s warm-up,
measured by the session's cs2game.sh driver (Steam restarted per run with
the launcher's environment; the game killed at the end).

3. What the game's threads do in a stall
----------------------------------------
A watchdog on the frame-time file (no growth for 400 ms) runs `sample <pid> 1`.
Round-start stalls (run 7, 8 samples), leaf frames of the busy thread:
  __ulock_wait (futex)                        8-49 %
  JIT-code (FEX output)                       4-37 %
  lxrt_rewrite_range_code <- lxrt_jit_set_write   5-24 %
  readlink <- lxrt_mounts_translate <- through_root_symlinks   3-25 %
Two runtime overheads, both measured, both fixed below.

3a. readlink per path prefix. through_root_symlinks() (runtime/mounts.c)
walked /a, /a/b, ... of every absolute path of every path syscall with one
readlink() each, to resolve the --symlink entries of the sandbox root in
guest terms. A game opening thousands of assets paid 2-6 syscalls per
lookup. Fix: a 512-slot prefix cache (2 s TTL, dropped by this process's
mkdirat/unlinkat/renameat/symlinkat/linkat; LXRT_NO_SYMCACHE=1 disables).

3b. The rescan of FEX's JIT output. Every FEX write into its code buffer is
wrapped in a WriteScope (FEXCore/include/FEXCore/Utils/LxrtJit.h) that
names the exact range written; the runtime scans it for the sites Darwin
cannot run as emitted (the inline getcpu `svc`, `mrs CNTVCT_EL0` for rdtsc,
x18). The scan went through a per-region dirty window shared by all
threads: one thread's 4-byte branch patch far from another thread's new
block made the union cover the distance between them. Counted with the new
sigstats fields (per 5 s window, the game's process):
  loading:  186442 calls  254440 Kwords (1.0 GB) ... 58597 calls 767503 Kwords (3.1 GB)
  playing:    2051 calls   75711 Kwords (0.3 GB) ...  4239 calls 222183 Kwords (0.9 GB)
i.e. ~50 K words scanned per 4-byte patch during play. LXRT_NO_RESCAN=1
(unsafe: svc sites) as the upper bound of the gain, run 9 vs 6/7: first
20 s stalled 11.0 s (13.7/15.8), stalls >150 ms 10 per 150 s (15 per 90 s),
1% low 33.0 fps (18.8-20.8), 0.1% low 11.9 (3.9-4.1). Fix: scan exactly the
scope's own range (rescan_exact in runtime/jit.c); the shared window only
collects pages noted by write faults. (The old union could also hand a
range still being written by one thread to another thread's scan, and the
writer then found nothing left to scan: a missed svc site is a Darwin
syscall executed with Linux arguments.)

5. KosmicKrisp leaked one object per render pass
------------------------------------------------
`heap` of the game's process at four minutes (run 11): 2,247,105
MTLRenderPassColorAttachmentDescriptorArrayInternal, 215 MB, next to 199,205
untyped malloc blocks (800 MB) and the Metal textures. Only 5
MTL4RenderPassDescriptor alive, so the arrays were not held by descriptors:
the bridge made each descriptor with [[MTL4RenderPassDescriptor new] init]
-- -init run a second time on an initialized object -- and the second init
replaces the attachment array without releasing the first. Measured in
isolation (scratch mtl4leak.m): 200,000 [[new] init] descriptors +19 MB of
footprint, 200,000 [new] +128 KB. Patch kosmickrisp-23 initializes the
five descriptor kinds once. With ~90 render passes a frame this was ~9 MB a
minute of memory that is never given back while the game runs.
6. Argument tables: one per VkCommandBuffer, 96 KB each
------------------------------------------------------
The same heap: 3,530 AGXG16GFamilyArgumentTable (one MTL4ArgumentTable per
VkCommandBuffer, made at creation and kept until destruction; Metal keeps
96 KB behind each whatever its three bindings): the game keeps thousands of
command buffers allocated. Metal snapshots a table's contents when a draw,
dispatch or execute command is encoded (MTL4RenderCommandEncoder.h), so a
table is needed only while its command buffer records. Patch kosmickrisp-24:
borrowed from a device pool at vkBeginCommandBuffer, returned at
vkEndCommandBuffer / reset / destroy. Run 13: 14 tables alive (3,530),
footprint 7.1 GB (7.6), peak 7.6 GB (8.5). The 96 KB untyped blocks are
something else (4,375 of them, 410 MB): attribution next.

runs 12-13 (agents' GPU tests running concurrently, numbers not comparable):
12   + patch 23                       150 s   56.5     8.9     1.6       23        13.5 s
13   + patch 24                       150 s   72.7     12.6    1.9       21        13.7 s

Confirmed in run 12 (patch 23 installed): 2 MTLRenderPassColorAttachmentDescriptorArrayInternal alive at four minutes (2,247,105 before). The untyped malloc blocks stay (221,130, 925 MB, ~4 KB each): the next memory item.

7. The rescan of pages noted by write faults (2026-10-07)
---------------------------------------------------------
A watchdog on the frame-time file, now written per present
(LXRT_VK_FRAMETIMES_SYNC=1), `sample`s the game 200 ms into a stall. A 1.9 s
gameplay stall: the game's first thread in lxrt_jit_set_write -> rescan ->
lxrt_rewrite_range_code for every sample. Section 3b made each write scope
scan its own range; the pages FEX writes outside its scopes (noted by write
faults, one page each) still went into the region-wide lo..hi window shared
by every thread, and two pages far apart made one rescan read most of the
code buffer. They are now a list per thread (write mode is per thread),
scanned page by page (runtime/jit.c rescan_written_pages).

8. Command allocators made and destroyed (KosmicKrisp)
------------------------------------------------------
The other stalls: the render thread waiting on the GPU 1.3 s
(kk_timeline_wait) while Metal's dispatch queue finalized IOGPU resources of
deallocated MTL4CommandAllocators. KK_ALLOC_LOG=1, every 5 s of gameplay:
made ~800, released ~800 (29 GB of allocator memory), idle 1-10 of a 256 MB
pool, largest allocator given back 91 MB. Allocators never shrink and the
pool handed them out last-in-first-out, so every one grew to the largest
command buffer any had served.

9. Why the allocators were that large: Metal command buffers
------------------------------------------------------------
Metal 4 directly (scratch mtl4alloc.m): one command buffer of 3000 draws
2.4 MB of allocator memory; 3000 draws with every render state changed per
draw 3.8 MB; 30 command buffers of 100 draws on one allocator 69.6 MB, and
+117 MB of process footprint once executed. A command buffer costs ~2.3 MB
whatever it holds. KosmicKrisp made ~9,700 Metal command buffers a second in
Counter-Strike 2 (~72 a frame): the render passes' shared command buffer was
closed by `close_gfx_cmd_buf` ~53 times a frame, set at every barrier
between passes in case work hoisted before a pass (predicates, unrolling,
tessellation) would come after it -- work this game hardly records.
Patch kosmickrisp-25: the dependency is noted and a draw that hoists work
after one splits the pass there (before its encoder is used); allocators
are asked for by the size their command buffer needed last time, the pool
(768 MB) forgets the one unused longest. Patch kosmickrisp-24 also gave a
replayed recording (second submit of a command buffer) an argument table
(tests/elf/run_vk_arm64.sh vk_resubmit, 48 passed).

11. Game Mode: reachable, and harmful here (not enabled; see 12)
--------------------------------------------------------
The game's window belongs to SteamARM-X11.app. What it took for macOS to
turn Game Mode on for it (each step MEASURED with gamepolicyd's log; a
notifyutil/`log stream --predicate 'process == "gamepolicyd"'` check, no
screen capture):
- the bundle's games category / LSSupportsGameMode (it said utilities);
- a process launched by Launch Services: exec'd directly X11.bin was
  anon<X11.bin> to RunningBoard (and, without CFProcessPath, a foreground
  app with no bundle to Launch Services), and gamepolicyd labels only app
  identities; X11.bin as CFBundleExecutable with the bundle signed ad hoc;
- a bundle at a new file node: gamepolicyd kept "not a game" for the node
  that had said utilities (the same bundle copied anywhere else was labelled
  at once: "Found game GameProcess(X11.bin, labelReason=LSSupportsGameMode)").
Then, with Counter-Strike 2 in its full-screen window (the overlay above the
menu bar, xquartz-ui-fullscreen-over-dock), "Full screen gaming session is
now active", "Game mode enabled". And the game got slower:
  Game Mode on, game launched outside the X server's coalition   39-42 fps, 1% low 3.5-4.9
  on, Steam+game started by the X server (a spawn service in it)  73 fps (median 6.9 ms), 1% low 1.6
  on, the same plus FEXServer, PulseAudio, PipeWire started by it 35 fps, 1% low 2.9
  off, the same spawn-service setup, bundle labelled utilities   140 fps, 1% low 48.1
Game Mode favours the frontmost game's coalition (a test app's own child
got 47 % more CPU than an outside process: 802k against 545k loop counts)
and gives the GPU and the display to the process that owns the full-screen
window -- here the X server, which only hosts the picture; the game renders
in its own lxrun process. With this architecture that is the wrong process,
so SteamARM leaves Game Mode off: X11 stays public.app-category.utilities
and is started as before. Kept for later in ~/SteamARM-build/gamemode-
experiment (not in the repo): the spawn-service patch, tools/x11spawn and
the script changes. What would make it right is the game's own process
owning the full-screen window.
The HUD's "Composited": the overlay is a window of the X server showing a
layer of the game's process; macOS does not scan it out directly. The
display here is 60 Hz (CGDisplayCopyAllDisplayModes: max 60.00 Hz): the
HUD's frame interval cannot be below 16.67 ms on it.

12. Game Mode on: the Metal HUD was the culprit
----------------------------------------------
Game Mode is on now: SteamARM-X11.app is in the games category and started
by Launch Services, and the launcher starts Steam -- and so every game --
FEXServer, PulseAudio and PipeWire through the X server's spawn service
(patches/xquartz-game-mode.patch, xquartz-spawn-service.patch,
tools/x11spawn, scripts/run-app.sh in_x11), in the coalition of the game
macOS sees. Section 11's slowdown had one cause, and it was not the
architecture.
Under Game Mode the game produced a third of the frames without waiting on
anything measurable: GPU busy 30-60 % of the time (KK_ALLOC_LOG's new
per-5 s GPU time, from Metal's commit feedback), acquire 0.1 ms, the X
server idle, single-thread loops inside and outside the X server's
coalition as fast as without Game Mode, 1 ms sleeps exact. lsappinfo,
during a run, listed the game's process: "lxrun", type BackgroundOnly --
an application of its own. It was only there with the HUD on: the HUD's
main-queue blocks call +[NSApplication sharedApplication] (its keyboard
shortcuts, HUDKeyboardHookInit) and +[NSScreen mainScreen] (refresh rate,
safe area: -[HUDMTLLayerTracking _updateInfrequentFields]); both reach
HIServices' _RegisterApplication (lldb, a window-less Metal 4 test with
the HUD on: registered after the first CFRunLoop slice). Game Mode then
ranks the game it recognises -- the X server -- above that "other" app,
which is the one drawing the frames.
Metal HUD off, same setup:
  Game Mode on   94.4 / 126.6 fps   1% low 10.6 / 51.1
  Game Mode off  72.9 / 128.4 fps   1% low  1.9 / 42.1
runtime/window.m now answers the HUD's two calls itself, only when they
come from libMTLHud and the process has no window of its own: no NSApp
(a game's keys go to the X server; the HUD's shortcuts never worked here)
and a stand-in screen built from CoreGraphics (refresh rate from the
display mode, no safe area; anything else NSScreen answers comes back
zero). Nothing registers (lsappinfo: no lxrun), the HUD draws as before.
Metal HUD on, Game Mode recognised for the X server (spawn service):
  before (section 11)  30-53 fps, 1% low 1-4
  Game Mode on   140.1 / 117.3 fps   1% low 35.4 / 32.4
  Game Mode off   97.8 / 105.2 fps   1% low  6.2 / 14.4
  later, the Mac in use between runs (4 GB of 5 in swap): on 80.1 / 74.8,
  off 76.9 -- the whole machine slower, and Game Mode no longer a cost.
This bench varies by run (the same setup gave 72.9 and 128.4 above); only
the 30-53 fps of the HUD under Game Mode was repeated in every run.
The installed 0.3.55 (SteamARM.app's setup: the X server from Launch
Services, the spawn service, HUD on, Game Mode on; no one using the Mac):
  91.1 / 92.3 fps, 1% low 51.4 / 40.6, frames over 100 ms 0 / 1 in 40 s,
  lsappinfo: no lxrun
  the same install with LXRT_HUD_APPKIT=1 (the HUD's AppKit calls as
  before): 130, 100, 191 frames per 2 s, then 11, 8, 20, then none -- the
  game stopped presenting 20 s into the match.
The HUD's "Game Mode On/Off" is system-wide: FramePacing's
FPMTLMetricsGameModeEnabled reads the com.apple.system.console_mode_changed
notification's state, so the HUD in the game's process shows On while the
X server is the game in full screen.
Also from CodeWeavers' sources (CrossOver 26), as
their Wine and DXMT do:
- the X server holds an NSProcessInfo activity (user-initiated,
  latency-critical) for its whole life (patches/xquartz-app-nap.patch): no
  App Nap for the application that shows the game, also while another one
  is in front. No difference measured with the game in front (66.9 fps
  against 74.8-80.1, one run). The same activity in the process that draws
  the game registered nothing (lsappinfo) and changed nothing (73.3 / 76.0
  against 80.1 / 74.8): not kept, a process that is not an application is
  never napped;
- KosmicKrisp asks Metal's compiler service for as many compilations at
  once as it can run (shouldMaximizeConcurrentCompilation, patch 25):
  new pipelines from Source 2's job threads compiled one after another.
Not taken: displaySyncEnabled=NO (the window server takes one drawable
per refresh of a remote layer whatever it says, stage 52; shim/mailbox.c
already never makes a game wait), msync (Windows games only; ntsync is
emulated already, runtime/ntsync.c), per-thread Mach priorities
(guest scheduling calls are translated already; LXRT_QOS=interactive
measured no gain, stage 51).
