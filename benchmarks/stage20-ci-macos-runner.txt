3. x18 is preserved for a binary built against a pre-13 SDK
------------------------------------------------------------
tests/x18_preserve/run.sh builds one program twice and checks x18 across
preemption (8 threads spinning), a SIGALRM handler, 1000 sched_yield and a
300 ms usleep. MEASURED on the runner:

    build/x18_preserve_cur    (LC_BUILD_VERSION sdk 15.5)
      preemption, threads 0-7            x18 CHANGED
      after SIGALRM handler              x18 = 0  ZEROED
      after 1000 sched_yield             x18 = 0  ZEROED
      after usleep(300 ms)               x18 = 0  ZEROED
      => x18 is NOT preserved for this binary
    build/x18_preserve_sdk12  (LC_BUILD_VERSION sdk 12.3)
      preemption, threads 0-7 (~3500 loops each)  x18 = 0x5a18c0de12345678  PRESERVED
      after SIGALRM handler              PRESERVED
      after 1000 sched_yield             PRESERVED
      after usleep(300 ms)               PRESERVED
      => x18 is preserved for this binary

This is what benchmarks/stage19 §3a predicted from xnu's
machine_task_process_signature() ("temporary override for tasks before
macOS 13"), now observed on macOS 15.7.

What it would mean, as a HYPOTHESIS until measured on the M4 / macOS 27:
- lxrun linked with -Wl,-platform_version,macos,12.0,12.3 would keep a guest's
  x18 across context switches;
- the x18 rewriting of runtime/x18.c could then become optional; today it
  covers libcef's `blr x18` and every other x18 use in Linux code;
- the ARM64 Windows ABI (TEB in x18) would no longer be blocked by x18. That is
  one of the two ARM64 Proton blockers in stage19 §2; the 0x7ffe0000 one is
  unaffected.

Still to check before relying on it:
- the same measurement on the M4 under macOS 27;
- that nothing in lxrun depends on the 1 GHz timebase that a pre-fall-2024 SDK
  turns off (stage19 §3a: the runtime must use mach_timebase_info);
- whether an sdk-12 lxrun keeps every entitlement and API it uses (MAP_JIT with
  allow-jit, the Metal remote layer).
