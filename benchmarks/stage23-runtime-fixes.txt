1. The W/X livelock of 4 KiB sub-pages
--------------------------------------

What it was (MEASURED + VERIFIED IN SOURCE, runtime/subpage.c at 50998f6).
A 16 KiB host page holding a guest code page (r-x) and a writable guest data
page (rw-) of a 4 KiB-aligned image wants rwx. Darwin refuses write+execute
outside MAP_JIT, so the page is rw- or r-x at any moment and the fault
handler flips it: a store fault -> rw-, an instruction fetch fault -> r-x.
A store executed from that page into that page needs both at once. With
LXRT_SUBPAGE_LOG=6 on build/subpage4k selfwrite (main):
  subpage flip: pc 0x1056fa268 addr 0x1056fb280 -> write
  subpage flip: pc 0x1056fa268 addr 0x1056fa268 -> exec
  ... the same pair forever (killed by the 5 s deadline, rc 142).
Real-world exposure: every 4 KiB-aligned aarch64 executable or library whose
code at the end of its text writes data at the start of its data segment in
the same 16 KiB page (the task brief counts 25 executables and 21 libraries
4 KiB-aligned in the Steam Frame root; not re-measured here).

Design (VERIFIED IN SOURCE, runtime/storemu.c, runtime/subpage.c).
- On a data abort with WnR set (ESR bit 6) whose pc lies in a W/X-split
  host page, the handler decodes the instruction. If it is a store whose
  bytes touch that page, the handler performs it: it checks the guest
  protection of every 4 KiB page written (a page the guest did not make
  writable -> a real fault, as on Linux), mprotects the split page(s) rw-
  while the thread is parked in the handler holding the sub-page lock,
  stores, mprotects r-x again, updates result/writeback registers and
  advances pc. The host page is never writable and executable at once.
  Other threads that run into the page meanwhile wait on the lock in their
  own fault handler and find it executable again.
- Covered: STR/STRB/STRH/STUR/STTR (unsigned offset, unscaled, pre/post-
  index, register offset with UXTW/LSL/SXTW/SXTX), SIMD&FP STR/STUR B-Q,
  STP/STNP (W, X, S, D, Q), ST1-ST4 (multiple and single structure, post-
  index by immediate or register), STLR/STLLR/STLUR, LSE LD<op>/ST<op>
  (ADD, CLR, EOR, SET, SMAX, SMIN, UMAX, UMIN), SWP, CAS, CASP, DC ZVA.
  Atomics are performed with host atomics on the same memory (atomic
  against other threads); plain stores keep per-element single-copy
  atomicity; every emulated access is bracketed by full barriers.
- Exclusives. The monitor does not survive the fault (MEASURED, probe
  monitor.S: 64 of 64 STXR fail when a first-touch page fault falls between
  them and their LDXR, 0 of 64 with a plain load there instead). So STXR is
  performed as a compare-and-swap against the value its LDXR loaded:
    way 1: the LDXR's destination still holds it (nothing between the two
           can write it or the base) -> CAS against that register;
    way 2: the loop body overwrote it (clang: `ldaxr w8,[x9]; add w8,w8,w0;
           stlxr w10,w8,[x9]; cbnz w10,<ldaxr>`), and the instruction after
           the STXR is `cbnz Ws, <the LDXR>`: then re-running the loop from
           the LDXR with the current registers is exactly the guest's own
           retry after a failed store-exclusive, so the handler performs
           that retry: atomic load, the body interpreted (add/sub/adc/sbc,
           logical imm/reg, mov wide, bitfield, csel family, ccmp, variable
           shifts, madd/msub, conditional branches, barriers; no memory
           access), CAS; repeated until the CAS succeeds or the body
           branches out; registers, flags and pc committed as the guest
           would have them.
  Like QEMU user mode, this accepts ABA. Neither way applies -> refused.
- Refused forms keep the old flip and print, at most 8 times a process,
  "[lxrt] subpage: store at pc ... cannot be emulated (<why>): W/X flip".
- Rescan rule (was missing on this path; MEASURED below). Code stored into
  an executable 4 KiB guest page is rewritten before it runs: after an
  emulated store into one (the guest page must be guest-writable, i.e. the
  guest mprotected it rwx), and at every write->execute flip of a split page
  (the page was writable, so any executable 4 KiB page in it is rescanned).
  lxrt_rewrite_has_candidates() (rewrite.c) pre-checks each 4 KiB page for
  the only patterns classify() can match (`svc #0`; MRS/MSR with op0 = 3),
  so unchanged code costs a vectorised compare, not a scan. Gated by
  g_rewrite_mapped, as mapped code is; LXRT_NO_RESCAN=1 turns it off, as it
  does for JIT output.
- Not changed: a store from ANOTHER host page into a split page still flips
  it rw- (and can still write the guest's r-x 4 KiB page in it: the leak the
  subpage.c header documents). mprotect(PROT_EXEC) of a sub-page range does
  not rewrite (lxrt_subpage_mprotect); the next write->exec flip rescans it,
  a direct rw-(unflipped)->r-x mprotect does not. UNKNOWN whether any guest
  does that; not addressed here.

2. Relative /proc/self/exe
--------------------------

What it was (VERIFIED IN SOURCE, runtime/procfs.c:288 and main.c:472 at
50998f6): g_exe was the program path exactly as lxrun got it, and the
procfs "exe" symlink pointed at it. Started by a relative path, readlink
returned a relative path, and static glibc asserted:
  Fatal glibc error: ../sysdeps/unix/sysv/linux/dl-origin.c:42
  (_dl_get_origin): assertion failed: linkval[0] == '/'   (rc 134, MEASURED)
Two more consequences (MEASURED with tests/elf/proc_self_exe.c on main):
open("/proc/self/exe") failed for a relative name (the kernel resolves a
relative link target against the procfs directory) and for an absolute
guest path under LXRT_ROOT (the target was the guest path, followed as a
host path).

Fix (VERIFIED IN SOURCE, main.c, procfs.c, dispatch.c LNR_readlinkat):
- A relative name becomes realpath() of the loaded image, in guest terms:
  lxrt_mounts_untranslate (LXRT_ROOT or a bind) or, outside both, the host
  path (which is then also the guest path). Symlinks resolved, as Linux.
- The procfs link points at the image's host path whenever the guest's name
  is not one (relative names; guest paths under LXRT_ROOT or a bind), so the
  host kernel's open() reaches the file.
- readlink of this process's procfs exe link answers with the guest's name,
  so an absolute name reads back exactly as before, and what a re-exec of
  /proc/self/exe runs (lxrt_proc_exe_path, FEX) is unchanged for absolute
  names. Other processes' /proc/<pid>/exe follow the link target through
  readlinkat's usual root/bind untranslation.

Tests (tests/elf/run.sh), MEASURED main -> new, "== proc self exe: ok"
means readlink absolute and as expected, realpath equal, open of
/proc/self/exe and of the returned name both read an ELF header:
  build/proc_self_exe                   (relative)          134 -> 0
