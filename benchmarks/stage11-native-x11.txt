Stage 11 / W1 -- native-window X server: XQuartz (xorg-server hw/xquartz)
built from source for macOS arm64, rootless, on display :2.
Apple M4, macOS 27.0 (26A428), Xcode clang 21.0.0. 2026-09-26.

VERDICT: YES. Our own build of the XQuartz DDX (upstream xorg-server
21.1.24, MIT) runs as ~/SteamARM-build/xquartz/SteamARM-X11.app, without
sudo, without the XQuartz.app package and without launchd. It listens on
/tmp/.X11-unix/X2, and every mapped X11 toplevel becomes a real macOS window
owned by the server process (CGWindowList, bounds = X geometry shifted down by
the menu bar). Host X clients (xdpyinfo, xterm, xeyes, a GLX test program, and
MIT-SHM tests) work against it. Two small source patches were needed
(log path, SIGTERM handling). Xvnc (:1) is untouched; Linux guests are NOT
connected to :2 yet (see NEXT).
[MEASURED]

HOW THE SERVER STARTS WITHOUT XQuartz.app / launchd  [VERIFIED IN SOURCE +
MEASURED]
  hw/xquartz/mach-startup/bundle-main.c main():
    - checks in / registers the Mach bootstrap service
      "<bundle-id-prefix>.X11" = org.steamarm.X11
    - fork()s twice; the grandchild runs startup_trigger(): if argv[1] starts
      with ':' it behaves "like a normal DDX": bootstrap_look_up() and sends
      argv/envp over MIG (start_x11_server)
    - the parent sits in mach_msg_server(); do_start_x11_server() ->
      server_main() -> X11ControllerMain/X11ApplicationMain: NSApplication on
      the main thread, dix_main() on a second thread (quartzStartup.c).
    - no launchd socket was handed off, so DISPLAY is unset and the server
      listens on the normal unix socket /tmp/.X11-unix/X<N>.
  So running Contents/MacOS/X11.bin :2 directly from the bundle is enough:
  NSBundle.mainBundle resolves to the .app, it gets a Dock icon and menu
  (LaunchServices shows it as "SteamARM-X11", type Foreground).
  Side effects:
    - the grandchild stays blocked forever in the start_x11_server RPC (the
      server never replies because server_main does not return). Harmless;
      the launcher kills it on stop.
    - one instance per bundle: the Mach service name is fixed, so a second
      display needs a second bundle / bundle-id-prefix.
    - log: XQuartz forces ~/Library/Logs/X11/<bundle-id-prefix>.log;
      patch 1 adds XQUARTZ_LOG_FILE, the launcher points it at
      ~/SteamARM-roots/logs/x11-native.log (previous run -> .old).
    - preferences domain org.steamarm.X11 (user defaults of our own bundle
      only). The launcher sets rootless=1, nolisten_tcp=1, no_randr_alert=1
      (otherwise a RandR mode switch pops a modal "Enter RandR mode?" panel),
      no_quit_alert=1, window_item_modifiers=command (see PROBLEMS).
  Server command line used by the launcher:
      X11.bin :2 -nolisten tcp +iglx          (env XQUARTZ_LOG_FILE=...)
  +iglx is required for indirect GLX (off by default since 1.19); Linux
  guests can only use indirect GLX against this server.

PATCHES (patches/xquartz-*.patch, applied by build-xquartz.sh)
  xquartz-log-file-env.patch   hw/xquartz/darwin.c OsVendorInit: honour
      $XQUARTZ_LOG_FILE instead of ~/Library/Logs/X11/<prefix>.log.
  xquartz-signals-to-server-thread.patch   hw/xquartz/quartzStartup.c:
      block SIGTERM/SIGINT/SIGHUP/SIGQUIT in server_main() (main thread,
      before AppKit or anything else spawns threads) and unblock them only in
      server_thread(). Without it SIGTERM usually lands on another thread;
      GiveUp() then only sets dispatchException and the dix thread keeps
      sleeping in poll() until a client happens to connect/send something.
      Measured: with xeyes+xterm connected, 5/5 stops needed SIGKILL after 20 s
      (an earlier attempt that only extended the existing SIGALRM/SIGBUS
      block after pthread_create was also 5/5 hung); with this patch 5/5
      clean exits in 0.22 s. An idle server (no clients ever) exited fast
      even before the patch.

WHAT WORKS  [MEASURED, host clients, DISPLAY=:2]
  xdpyinfo: vendor "The X.Org Foundation", X.Org version 21.1.24, screen
    1920x1050 (= 1920x1080 display minus menu bar), depth 24, 64 visuals,
    21 extensions:
      Apple-DRI Apple-WM BIG-REQUESTS DAMAGE DOUBLE-BUFFER GLX
      Generic Event Extension MIT-SCREEN-SAVER MIT-SHM Present RANDR RENDER
      SHAPE SYNC X-Resource XC-MISC XFIXES XINERAMA XInputExtension
      XKEYBOARD XVideo
    Requested checklist: MIT-SHM yes, GLX yes, RANDR yes, XKEYBOARD yes,
    RENDER yes, Composite NO (see below).
  Native windows: xterm, xeyes and a GLX window each appear as one window of
    the server pid in CGWindowListCopyWindowInfo, layer 0, e.g.
      X: xeyes 200x150+100+100  -> CG wid 10866, bounds 100,130 202x152
      X: xterm 484x316+400+200  -> CG bounds 400,230 486x318
      X: glxtest 256x256+300+300 -> CG bounds 300,330 256x256
    (+30 px y = menu bar; +2 px = X border width). The X server publishes
    the CGWindowID on each toplevel as property _NATIVE_WINDOW_ID
    (xprop: _NATIVE_WINDOW_ID(INTEGER) = 10866 == CG wid). onscreen=1 while
    the desktop Space is visible; while a fullscreen app owned the active
    Space the same windows reported onscreen=false and CGSCopySpacesForWindows
    put them on Space 1 (desktop) -- i.e. that was the Space, not the server.
    Captured via ScreenCaptureKit (window filter): xterm text rendered with
    the misc "fixed" font, xeyes shaped (non-rectangular) window, GLX window
    green. XGetImage read-back of xterm/xeyes also correct.
  Fonts: -fp built-ins alone already gives "fixed" + "cursor"; the prefix
    misc/cursor dirs + fonts.alias are in the default font path.
  XKB: the keyboard map is synced from the macOS layout: xmodmap -pke shows
    114 keys (keycode 8 = a A aring Aring, ...), modifiers shift/lock/control,
    mod1 = Mode_switch (Option), mod2 = Meta (Command).
  GLX (Homebrew mesa libGL client, built with Apple GLX support):
    direct (Apple-DRI):  isDirect 1, GL_RENDERER "Apple M4",
                         GL_VERSION "2.1 Metal - 91.7", readback OK
    indirect (LIBGL_ALWAYS_INDIRECT=1, needs +iglx): isDirect 0,
                         GL_RENDERER "Apple M4",
                         GL_VERSION "1.4 (2.1 Metal - 91.7)", readback OK
    Linux guests (Mesa over FEX) can only use the indirect path: GL 1.4
    fixed-function over the wire. Useless for games; fine for Steam's
    occasional GLX probing. Vulkan must not go through GLX (see NEXT).
  MIT-SHM 1.2, shared pixmaps = yes:
    - SysV (shmget/XShmAttach/XShmPutImage 256x256): OK
    - fd passing (xcb_shm_attach_fd with an 8 MiB mkstemp+mmap segment,
      then ShmCreatePixmap + GetImage): OK. SHM_FD_PASSING is on because
      XTRANS_SEND_FDS is set (unix socket SCM_RIGHTS).
    macOS SysV limits here: kern.sysv.shmmax 4 MiB, shmseg 8, shmmni 32
    (changing needs sudo). A 1920x1080x4 frame (8.3 MB) cannot be a SysV
    segment, so guests should use the fd path (xcb_shm_attach_fd /
    memfd) -- the runtime must pass the fd through SCM_RIGHTS as a Darwin
    fd the server can mmap. [SysV limits MEASURED via sysctl; guest
    behaviour HYPOTHESIS]
  Idle cost: 0.0 % CPU, ~130 MB RSS with no clients.
  Launcher: start/start (no-op)/status/stop/stop (no-op)/restart all
    behave; :1 is refused; ready in < 1 s.

WHAT DOESN'T / PROBLEMS
  - Composite is absent on purpose: bundle-main.c main() sets
    noCompositeExtension = TRUE (xserver issue 1409, rootless + Composite
    crashes). Compositing managers and ARGB-visual transparency won't work.
    [VERIFIED IN SOURCE + MEASURED]
  - No window manager. quartz-wm (part of XQuartz.app, separate repo) is not
    built, so toplevels are undecorated native windows (no title bar, can't
    be dragged by the OS). Steam draws its own frame; games are usually
    fullscreen. Building github.com/XQuartz/quartz-wm is a possible W1b.
  - XKB log noise: every keyboard (re)init logs
      (EE) Error loading keymap .../server-2.xkm
      (EE) XKB: Failed to load keymap. Loading default keymap instead.
    Cause: XQuartz asks for rules base / model empty / layout empty
    (darwin.c); with xkeyboard-config 2.48 that keymap has no symbols
    section (xkm "present" = 0x7b, bit 2 missing), XkmReadFile's need-check
    fails and the server falls back to its built-in map, which XQuartz then
    overwrites with the macOS layout. Functionally fine (see XKB above), but
    keycodes are macOS virtual keycodes + 8 and unnamed (xkb_keycodes
    "empty", keys "<>"), not evdev. Clients that map physical keys by XKB
    key name / evdev keycode (Wine's scancode detection, SDL scancodes,
    libxkbcommon-x11) may mis-map keys; keysym-based input is fine.
    [MEASURED + VERIFIED IN SOURCE; guest impact HYPOTHESIS]
  - "fakebuttons: Unknown modifier "comando"": the Spanish localization
    translates the "window item modifiers" default string. Worked around by
    the launcher's window_item_modifiers=command default. [MEASURED]
  - xtrans prints "_XSERVTransmkdir: ERROR: euid != 0, directory
    /tmp/.X11-unix will not be created" when the dir is missing; the
    launcher creates it (mode 1777) first. [MEASURED]
  - A guest's /tmp is not the host's /tmp (Xvnc's socket lives at
    /tmp/lxrt-abstract-501/_tmp_.X11-unix_X1 via the runtime), so guests
    cannot see /tmp/.X11-unix/X2 yet. [MEASURED via lsof]
  - Relies on libXplugin (private, undocumented Apple API; XQuartz itself
    depends on it). If Apple removes it, the xpr backend needs a Cocoa
    replacement (which is the NEXT plan anyway).
  - Not measured: input from a real user (keyboard/mouse into X windows),
    multi-monitor, Retina/HiDPI scaling, RandR resolution changes, Steam or
    any guest client on :2, clipboard sync (xpbproxy thread runs).

WHERE NATIVE WINDOWS ARE CREATED (for CALayerHost / remote layers per X
window)  [VERIFIED IN SOURCE]
  Generic rootless layer (miext/rootless/):
    rootlessWindow.c  RootlessRealizeWindow() -> RootlessEnsureFrame() ->
      SCREENREC(pScreen)->imp->CreateFrame(winRec, ...) for every top-level
      (child of root) window when it is mapped; RootlessDestroyFrame,
      RootlessPositionWindow/Resize/Restack/Reshape follow the X window.
    rootless.h  RootlessFrameProcsRec = the backend vtable: CreateFrame,
      DestroyFrame, MoveFrame, ResizeFrame, RestackFrame, ReshapeFrame,
      UnmapFrame, StartDrawing/StopDrawing (lock backing store, fb draws
      into it), UpdateRegion/DamageRects (flush), SwitchWindow,
      DoReorderWindow, HideWindow, UpdateColormap, CopyBytes, CopyWindow.
  XQuartz backend (hw/xquartz/xpr/, libXplugin):
    xprFrame.c  xprRootlessProcs (line ~448) registered by xprInit() ->
      RootlessInit(). xprCreateFrame() -> xp_create_window() (line ~194)
      creates the native window; xprSetNativeProperty() stores its
      CGWindowID in _NATIVE_WINDOW_ID; xprStartDrawing -> xp_lock_window
      (CPU backing store), xprStopDrawing/xprUpdateRegion -> xp flush;
      xprIsX11Window()/xprGetXWindow() map CG window numbers <-> X windows
      (used by X11Application.m event routing).
    xprScreen.c  screen/pseudoramiX setup (xprAddScreen, xprDisplayInit).
    dri.c  Apple-DRI: xp_create_surface(wid, ...) creates an Xplugin
      *surface* attached to an X window (DRIUpdateSurface / DRICreateSurface)
      -- this is the existing "GPU content inside an X window" mechanism.
    GL/indirect.c  server-side GLX: xp_attach_gl_context(ctx, sid) binds a
      CGL context to that surface; surface_notify() tracks moves/resizes.
  Cocoa side: X11Application.m (NSApplication subclass, event loop, sends
    events to dix via darwinEvents.c), X11Controller.m (menus/prefs),
    quartz.c (show/hide, fullscreen, RandR glue in quartzRandR.c).
  Options for Vulkan-per-X-window (HYPOTHESIS, to evaluate next):
    a) Minimal: keep xpr, look up the X window's CGWindowID
       (_NATIVE_WINDOW_ID) and put a borderless child NSWindow / layer-hosting
       view over it that hosts a CALayerHost(contextId) from the Vulkan
       process; track moves via the RootlessFrameProcs hooks. Cheap but two
       windows per toplevel.
    b) Replace xpr with a Cocoa RootlessFrameProcs backend (one NSWindow per
       frame, CALayer contents = backing store, plus a sublayer for a remote
       CAContext / CALayerHost). Full control, more code (the old
       "quartz/cr" Cocoa rootless backend in older xservers is a reference).
    c) Mirror Apple-DRI: a new surface type in the same place as
       xp_create_surface, backed by our layer instead of an Xplugin surface.
    Swapchain presentation for guest Vulkan would then bypass X entirely
    (X only provides the window + geometry), like Xwayland + dmabuf.
