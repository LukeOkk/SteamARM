Stage 27 -- Android's services and framework in the x86_64 root: binder and properties under FEX, an init, zygote64 and system_server, zero VM (2026-09-29)
==================================================================================================================================================================

ZERO-VM. No virtual machine, no guest kernel. Host: Mac mini M4, 16 GB,
macOS 27.0. Base: bc27c17 (stage 25/26: binder, properties, x86-64 ART under
FEX). Every Android program below is an unmodified x86-64 (or i386) file of
Waydroid's LineageOS 18.1 x86_64 image (/Volumes/SteamARMAndroid/root-x86_64,
benchmarks/stage25-art-x86-fex.txt), run by SteamARM's FEX under lxrun as an
ordinary macOS process. Nothing was signed in to, no Google component was
fetched, no Steam client was started, scripts/run-app.sh was not called.
Other agents ran guests on the same Mac at the same time (a display agent's
weston and Android root x86disp, the arm64 root's users); every process
below was started by this session and stopped by its own PID or process
group, or left by itself (property services, binder hubs, FEXServers, when
idle). Home paths are written as ~. Labels: MEASURED, VERIFIED IN SOURCE,
UPSTREAM DOCUMENTED, HYPOTHESIS, UNKNOWN.

Result
------
MEASURED:
1. Binder and properties work for x86-64 guests under FEX with no change to
   the binder driver or the property service: FEX passes the ioctls, the
   binder mmap, the property area mappings, the property_service socket and
   FUTEX_WAIT through to lxrun, and the structures are the same on x86_64
   and aarch64 (LP64). servicemanager, service list/check/call, dumpsys -l,
   vndservicemanager/vndservice, hwservicemanager (hwservicemanager.ready),
   lshal list and an x86-64 HIDL HAL all work; an x86-64 native service
   (tests/android/binder_service.c built against the image's own bionic)
   registers, answers, receives a file descriptor over binder (the hub's
   SCM_RIGHTS) and its death is noticed; getprop/setprop and
   __system_property_wait from x86-64 bionic work.
2. scripts/android-boot.py is a minimal init: it parses the image's 93 .rc
   files (91 services, 184 actions) as init does, runs init's boot triggers
   with a safe subset of actions, and starts a headless profile of 23
   services with their .rc command lines, sockets, environment and
   user/groups/capabilities, with init's restart rules; ctl.* from guests
   reaches it through the property service.
3. zygote64 (app_process64 -Xzygote, x86-64 ART under FEX with
   FEX_LOWWINDOW=1) preloads 12,100 classes in 1.2-1.9 s and listens on its
   init socket; it forks system_server, which specializes (setgroups,
   setresgid/setresuid to 1000, capset, seccomp policy under FEX's seccomp
   emulation, bind mount of /mnt/user/0 on /storage), gets its classpath
   compiled by installd + dex2oat64, prints "Entered the Android system
   server!" and runs the first 15 steps of startBootstrapServices, up to
   StartLightsService.
4. The wall: LightsService asks SurfaceControl for the internal display,
   which waits for SurfaceFlinger; SurfaceFlinger waits for the composer
   HAL; the image's only composer, Waydroid's hwcomposer.waydroid, is a
   Wayland client and exits with "Couldn't open Wayland display." After 60 s
   the framework's Watchdog kills system_server ("Blocked in handler on main
   thread ... SurfaceControl.nativeGetPhysicalDisplayIds ... LightsService
   ... <init>"), the zygote exits with it, and it all starts again. So
   sys.boot_completed is not reached, and PackageManagerService, which
   starts after the display (DisplayManagerService's
   PHASE_WAIT_FOR_DEFAULT_DISPLAY), never runs: no `pm list packages`, no
   `pm install`.
5. What it took: Android ids in the runtime (per-process virtual
   credentials, Linux's rules), five runtime fixes, one FEX patch (seccomp
   and CAP_SYS_ADMIN), host properties of the kind Waydroid's and Lepton's
   hosts set, and the boot script. tests/android/run.sh: 58 passed, 0
   failed, 2 expected failures (was 42 + 1); tests/elf: ANDROID_IDS added.

Part 2: an init (scripts/android-boot.py)
------------------------------------------
What it does, in order (the file's docstring has the rules):
- starts the property service itself (LXRT_PROPERTY_IDLE=0) with
  LXRT_PROPERTY_INIT=<state>/init.sock: runtime/propsvc.c now sends each
  property change and each ctl.* message there as a datagram and answers
  ctl.* with success, as Android's init queues them (without an init the
  old refusal stays);
- sets HOST_PROPS (below) before init's first action;
- tests/android/logd.py as logd's write socket (<state>/logcat.txt);
- parses /system/etc/init/hw/init.rc with its imports (init.environ.rc,
  init.usb*.rc, init.${ro.zygote}.rc = init.zygote64_32.rc), then
  /system/etc/init, /system_ext, /product, /odm, /vendor/etc/init and the
  APEXes' etc/: 93 files, 91 services, 184 actions. init.waydroid.rc's
  vendor.audio-hal, vendor.camera-provider-2-4 and vendor.hwcomposer-2-1
  come first, so the vendor files' definitions are the "ignored
  duplicates", as in init;
- runs early-init, init, late-init (which queues early-fs ... boot), then
  the property triggers: 1.8-2.1 s for all of it. Run: setprop, export,
  trigger, mkdir/write/copy/symlink under /data, /mnt and /storage,
  mount_all as Waydroid's init does it (ro.crypto.state=unencrypted,
  "nonencrypted" -> class_start main and late_start), start, stop,
  restart, class_start, class_stop, enable, exec_start. Counted and
  skipped: chmod 287, chown 140, copy 14 (outside those trees), exec 7,
  exec_background 4, exec_start 7 (not in the profile), write, mount,
  restorecon, wait_for_prop, load_persist_props (the property service
  loaded them), setrlimit and the rest;
- starts the services of the "headless" profile when an action asks:
  servicemanager, hwservicemanager, vndservicemanager; hidl_memory,
  vendor.configstore-hal, vendor.health-hal-2-0, system_suspend,
  vendor.power-hal-1-0, vendor.light-hal-2-0, vendor.memtrack-hal-1-0,
  vendor.gralloc-2-0, vendor.keymaster-4-0, vendor.gatekeeper-1-0,
  vendor.sensors-hal-1-0 (oneshot, exits 0 at once), vendor.vibrator-1-0;
  keystore, gatekeeperd, installd, credstore, idmap2d, audioserver,
  surfaceflinger; zygote. Each with the .rc argv, its sockets (bound in
  the root's /dev/socket by the script, passed as ANDROID_SOCKET_<name>;
  seqpacket becomes datagram, as lxrun does), init.environ.rc's exports
  plus setenv, a process group of its own (setpgid, as init), and
  LXRT_ANDROID_IDS from "user", "group", "capabilities" (AIDs from
  android_filesystem_config.h; all 96 names agree with bionic's getpwnam
  in the image, MEASURED with toybox id -u; "host" is waydroid.host.uid,
  default 1000). The x86_64 root's services get
  scripts/run-android-x86.sh's FEX environment and FEXServer; the zygote
  also FEX_NEEDSSECCOMP=1 (below);
- restarts: 5 s after an exit unless oneshot; "onrestart restart/setprop";
  a critical service with more than 4 exits in 4 minutes ends the boot;
  init.svc.<name>, ro.boottime.<name>; ctl.start/stop/restart and
  ctl.interface_start/stop (hwservicemanager's lazy-HAL requests) act on
  the table;
- stops every process it started, and what those left (found by the state
  directory in their environment), at the end.
Left out, with the reason the script logs: ueventd, logd (the stand-in),
lmkd, vold, apexd (flattened APEXes), netd, vendor.audio-hal(-2-0),
vendor.hwcomposer-2-1, zygote_secondary, bootanim, statsd, and the rest of
the .rc files' services (camera, drm, media, wifi, usb, tracing, ...).

Android ids (runtime/android_ids.c, .h)
---------------------------------------
What Android needs from credentials and namespaces, and Lepton gets from a
seccomp profile that answers success plus a bionic fake-uid patch
(docs/LEPTON_REUSE_ANALYSIS.md 3.3): LXRT_ANDROID_IDS=ruid[,euid,suid]:
rgid[,egid,sgid]:groups:eff,prm,inh,bnd,amb[:kn] ("root" for 0 with every
capability). With it:
- getuid/geteuid/getgid/getegid/getresuid/getresgid/getgroups report the
  virtual ids; setuid/setreuid/setresuid, setgid/setregid/setresgid,
  setfsuid/setfsgid, setgroups follow kernel/sys.c: CAP_SETUID/CAP_SETGID
  decide, the saved ids move as there, groups are kept sorted;
- capabilities: capget/capset (kernel/capability.c's subset rules),
  cap_emulate_setxuid on every uid change (keepcaps/SECURE_KEEP_CAPS,
  effective set on euid 0 <-> non-0), prctl PR_CAPBSET_READ (0..40, then
  EINVAL -- the zygote's drop loop ends on it), PR_CAPBSET_DROP,
  PR_SET/GET_KEEPCAPS, PR_SET/GET_SECUREBITS, PR_CAP_AMBIENT,
  PR_SET/GET_NO_NEW_PRIVS;
- execve: cap_bprm_creds_from_file for a file with no capabilities or
  set-id bits (saved = effective, root gets bounding|inheritable, others
  the ambient set, keepcaps cleared), carried in the next image's
  environment together with the bind table (LXRT_MOUNTS); fork copies it;
- chown/fchown/fchownat: a change Linux would allow these ids (CAP_CHOWN,
  or the owner's own uid and groups) reports success and leaves the file
  the Mac user's; the host's own ids are a real call;
- unshare of namespaces (CAP_SYS_ADMIN): 0, the same single view;
  mount with only propagation flags: 0; mount(MS_BIND): an entry in the
  per-process bind table of the bwrap emulation (mounts.c), MS_REMOUNT
  honoured for read-only; other mounts (tmpfs, filesystems): EPERM;
  umount2 of a bind removes it, otherwise EINVAL; setns EINVAL;
- other processes see them: /tmp/lxrt-shm-<uid>/android-ids (pid ->
  ids, checked against the process start time) answers SO_PEERCRED and
  SCM_CREDENTIALS for a peer with ids; runtime/binder.c's hello reports
  the virtual euid as the transaction sender's.
Without LXRT_ANDROID_IDS nothing changes (tests/elf ANDROID_IDS off).
tests/elf/android_ids.c, with LXRT_ANDROID_IDS=root: 38 checks in zygote's
order (unshare, MS_SLAVE, a refused tmpfs, a bind that shows the source's
file, chown with CAP_CHOWN leaving the owner, SO_PEERCRED of a child that
became 2000, the bounding set, setgroups sorted, keepcaps, setresgid/
setresuid 1000, capset down, ambient, chown and unshare refused without
the capabilities, no_new_privs, then an execve'd image with uid 1000,
groups, permitted = effective = ambient, keepcaps cleared, no_new_privs
kept, the bind still in place). Writing that test found one more runtime
fault: SO_PEERCRED of a fresh socketpair named a live FEXServer (a stale
entry in socket.c's sender table for a reused socket address); now a
closing socket drops its entry and a recorded sender must still hold the
socket (proc_pidfdinfo).

Deviations, stated rather than hidden
-------------------------------------
- Android ids are bookkeeping: every file stays the Mac user's (stat shows
  501), every process can signal every other one, a chown is not applied,
  a "namespace" is the one view there is. What Android asks and checks
  agrees with Linux; what the kernel would enforce is not enforced.
- /proc/self/fd hides FEX's descriptors by when they were opened (before
  the guest's first instruction); a descriptor FEX opens later is shown.
- The boot runs only the profile; exec/exec_background actions are
  skipped; no ueventd, logd, lmkd, vold, apexd, netd, tombstoned; no
  cgroups (libprocessgroup logs "CgroupMap::FindController ... failed" per
  process); /proc/sys, /sys/power, /sys/class are missing
  (android.system.suspend logs it and runs).
- The script's logcat is logd.py's: no pid per record, no logdr (no
  logcat client).
- seccomp is enforced by FEX's emulator, not a kernel; only for the zygote
  and its children (FEX_NEEDSSECCOMP=1 turns off FEX's inline syscalls:
  cost not measured).
