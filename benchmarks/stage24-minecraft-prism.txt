correctly yet: Java's JIT needs the opt-in x18 build (not yet validated for
the rest of SteamARM), and no 3.2 core path presents to a window. Details
and the ways forward: docs/MINECRAFT_INTEGRATION.md.

Two runtime defects stood in the way of Prism, both fixed, and one
diagnostic was added (MEASURED):
- inotify FIONREAD answered with the readiness pipe's byte count (1), not the
  size of the queued events. Qt reads exactly FIONREAD bytes from its blocking
  inotify descriptor; the window stayed blank and sample(1) showed the GUI
  thread in lxrt_inotify_read -> poll (P2). Fix: runtime/inotify.c
  lxrt_inotify_pending, runtime/ioctl_tty.c. Test: tests/elf/inotify_fionread.c
  (before: "FIONREAD after one create: 1", "read(fd, buf, 1) = -1 errno
  Invalid argument"; after: 32, "read(fd, buf, 32) = 32").
- An eventfd was two objects after fork(): the counter lived in process
  memory and only the token pipe was shared. Qt's QProcess (forkfd) parks the
  child in eventfd_read until the parent writes 42 and closes; the child saw 0
  with a readable pipe and spun at 99-100% CPU for ever (sample: 661 of 669
  samples in lxrt_eventfd_read), so Prism's QProcess never started anything
  ("Failed to start updater after 5 seconds. reason: QProcess::Timedout").
  Fix: runtime/epoll_eventfd.c, the counter and token flag in a MAP_SHARED
  page per eventfd, forks counted in the parent before fork. Test:
  tests/elf/eventfd_fork.c (HEAD's runtime: "child exit 142 after 5.00 s",
  4 FAIL; fixed: 10 OK, "20 x write-then-close in the parent: every child
  reads 42"). A first version counted the fork in the child and still hung
  Prism's child (P6: the parent closed before the child ran); the test's
  write-then-close case was added for that.
- (diagnostics) A guest fault outside the image now prints the instruction
  word and the hardware x18 (runtime/main.c fault_report): that is how the
  llvmpipe crashes below were read.

The bundle, and why it is not run as shipped (MEASURED)
--------------------------------------------------------
- `PrismLauncher` (a bash script) execs bin/prismlauncher = sharun
  (github.com/VHSgunzo/sharun): "ELF 64-bit LSB executable, ARM aarch64,
  statically linked", `llvm-readelf -l`: Type EXEC, LOAD at 0x400000. lxrun
  refuses ET_EXEC (runtime/elf.c: the low 4 GiB belong to macOS).
- Everything else is ET_DYN aligned at 64 KiB (survey of the install: 200
  DYN with LOAD align 0x10000, the 3 EXEC are sharun's hard links), so no
  LXRT_GUEST_PAGE=4096 is needed. The JRE likewise (libjvm.so, bin/java).
- sharun's job (VERIFIED IN SOURCE, sharun src/main.rs): run
  shared/lib/ld-linux-aarch64.so.1 --library-path <lib.path with + =
  shared/lib, then /usr/lib:/lib:/usr/lib64:/lib64...> --argv0 ... on
  shared/bin/<name>, after a userland exec that keeps /proc/self/exe on the
  sharun binary. scripts/guest/sharun-run.sh does the same with an ordinary
  exec.
- Consequence: /proc/self/exe is the loader, so Qt's applicationDirPath is
  shared/lib and Prism's root path is shared/ ("Binary path :
  /opt/apps/prism/shared/lib", "Application root path : /opt/apps/prism/shared"
  in its log). Prism looks for JavaCheck.jar in <root>/share/PrismLauncher
  (VERIFIED IN SOURCE, launcher/Application.cpp getJarPath, 11.1.1): the
  install adds shared/share -> ../share.
- The self-updater (shared/bin/prismlauncher_updater) is started by Prism as
  a plain ELF, without the bundle's library path: "Updater exited with
  unknown code 127" and an "Unknown Update Error" dialog (P7). The install
  removes it; SteamARM's installer decides versions.
- A data directory under the guest's /tmp made Prism warn on every start
  ("Your instance folder is in a temporary folder: '/tmp'!", MainWindow.cpp:
  pathfoldername.startsWith(QDir::tempPath())). Moving TMPDIR is not an
  option: lxrun itself uses TMPDIR as a host path for its /proc (A1 below).
  So HOME_IN_GUEST=/opt/apps/.prism-home.
- Every start without a signed-in Microsoft account opens the Quick Setup's
  "Add Microsoft account" page first (VERIFIED IN SOURCE, Application.cpp
  createSetupWizard: login = !anyAccountIsValid && SupportsMSA); "Finish"
  skips it. A fresh data directory adds the Language and Appearance pages.

Why (UPSTREAM DOCUMENTED, openjdk/jdk21u): R18_RESERVED is defined only for
__APPLE__ and _WIN64 (src/hotspot/cpu/aarch64/globalDefinitions_aarch64.hpp;
make/hotspot/gensrc/GensrcAdlc.gmk passes -DR18_RESERVED to ADLC for macOS
and Windows only); without it aarch64.ad leaves R18 out of the non-allocatable
classes and c1_FrameMap_aarch64.cpp maps r18 as a caller-saved register. So a
Linux JVM's compiled code uses x18 freely, and lxrun rewrites x18 only in
images it loads (runtime/x18.c), not in JIT output. HotSpot's stubs exclude
r18_tls explicitly (stubGenerator_aarch64.cpp) and the interpreter was
correct in every run here.
