Stage 28 -- an APK on the Mac's screen: the x86_64 Android root boots to sys.boot_completed=1 with its display, pm install, am start, the app's window in a macOS window, zero VM (2026-09-30)
===================================================================================================================================================================================================

ZERO-VM. No virtual machine, no guest kernel. Host: Mac mini M4, 16 GB,
macOS 27.0. Every Android program below is an unmodified x86-64 file of
Waydroid's LineageOS 18.1 x86_64 image run by SteamARM's FEX under lxrun,
as an ordinary macOS process; Weston is Fedora's aarch64 build under lxrun;
its X11 window on SteamARM's X server (:2) is a macOS window. No account
was signed in to, no Google component fetched, no Steam client started,
scripts/run-app.sh was not called with an app id nor with --stop. Other
agents ran guests on this Mac at the same time; experiments that wrote to an
Android root used APFS clones (/Volumes/SteamARMAndroid/x86apk, then the
session root /Volumes/SteamARMAndroid/session), never root-x86_64 itself,
and private binder/property/Weston/input directories. Home paths are ~.
Labels: MEASURED, VERIFIED IN SOURCE, HYPOTHESIS, UNKNOWN.

The APK: Simple Solitaire Collection 3.13 (de.tobiasbielefeld.solitaire,
versionCode 71, minSdk 11, targetSdk 25, no native code: dex only; F-Droid,
GPL-3.0; ~/SteamARM-roots/android/apk-samples, stage 25), picked with
scripts/apk-inspect.py as the sample that fits this root (API 30, x86_64):
of the others, F-Droid, Termux and Shattered Pixel Dungeon also carry x86_64
code (and arm64-v8a) and would run in the session too (not run here);
meritous and the fcitx5 plugins are 32-bit ARM, arm64-only or x86-only, or
have no launcher activity.

Found by running it, fixed here (each MEASURED):
- Services ran with the Mac's "/" as working directory: pm install failed
  with "INSUFFICIENT_STORAGE: Failed rename"
  (PackageManagerServiceUtils.makeDirRecursive walks "data", "data/app", ...
  relative, found none, tried mkdir "/data"). Now cwd is the root.
- sendfile and splice were ENOSYS: "failed to write; sendfile failed:
  ENOSYS" (PackageInstallerSession's staging copy, FileUtils.copy). Now a
  read/write loop with Linux's offset rules (runtime/dispatch.c;
  android_boot_rt: sendfile with and without an offset, splice file->pipe,
  splice with no pipe EINVAL).
- lmkd: without its socket, every oom_adj change waited 3 s for it with
  ActivityManager's lock held (ProcessList.writeLmkd); 56 "SLOW OOM ADJ:
  3000ms" and 3,100 "Failed to connect to lmkd" lines in the first boot, then
  ANRs of SystemUI and the network stack and "Lost network stack" took
  system_server down. A socket with a reader (commands dropped) makes the
  boot 22-26 s. The one command that waits for an answer, LMK_GETKILLCNT,
  comes only from dumps (VERIFIED IN SOURCE, the image's services.jar:
  ActivityManagerService.reportLmkKillAtOrBelow and dumpLmkLocked).
- AlarmManager "Too many (100000) false wakeups": BOOTTIME timerfds were
  measured against MONOTONIC, and here guest BOOTTIME runs 4.3 s behind
  guest MONOTONIC (MEASURED), so its elapsed alarms fired 4.3 s early, were
  re-armed and fired again. The timerfd now uses the guest's own clock id
  (android_boot_rt: an ABSTIME BOOTTIME deadline 80 ms ahead fires after
  83-86 ms).
- "Bad file descriptor" from BinderProxy.transactNative killed system_server
  0-5 times per boot (5 sessions: system_server started 2, 1, 2, 5, 1
  times; 4-141 failed binder calls logged per session) and apps more often.
  With diagnostics added (<binder dir>/client.log; the hub's log), the
  failing threads' channels "arrived closed at the other end" at the hub:
  the runtime passed the hub's end of a new thread's socketpair by
  SCM_RIGHTS and closed its own copy at once, leaving the message in flight
  as the only reference; XNU's unix-socket garbage collection (unp_gc, run
  by any close of a descriptor-carrying socket on the Mac) can flush such a
  socket (HYPOTHESIS for the mechanism, from the symptom). The runtime now
  keeps its copy until the hub has answered, and the hub keeps descriptors it
  passes on until the receiving thread's next request. After: 3 of 3
  sessions with no failed binder call and system_server started once each
  (MEASURED). But the hub still received a few channels "arrived closed"
  per boot (17 in one), and a thread whose channel that was then waited
  forever instead of failing: the first run of tests/android/run.sh's new
  session check had `am start -W` hang for its 300 s (MEASURED). So now the
  hub acknowledges every thread channel it registers (BH_THREAD_ACK,
  protocol version 2) and refuses one that arrives closed; the runtime waits
  up to 5 s for the acknowledgement and otherwise makes a new channel (4
  attempts, then EBADF). After: 3 sessions, no channel refused, no failed
  call, system_server started once each (MEASURED). UNKNOWN: why a channel
  arrived closed with the sender's copy still open (the XNU garbage
  collection is the HYPOTHESIS that the first fix was built on; the second
  does not depend on it).
- The Mac's safeguard (scripts/safeguard.sh) stops every lxrun guest past 80
  processes; Android is one per service and per app (60-80 after boot), and
  it did so three times during this stage's runs (00:53 in the interrupted
  session, 05:02 and 05:17 in this one), stopping the other agents' guests
  running then too. Now it allows SAFEGUARD_ANDROID_PROCS (100) more while an
  Android session runs (tests/launcher/safeguard.sh: 2 new checks; the
  running safeguard, another session's, keeps the old limit until it
  restarts), and the session disables 14 of the image's apps on its first
  boot (camera, gallery, music, clock, contacts, backup, print, sms push,
  DSU, deviceconfig, calendar, recorder, browser): 60 lxrun processes with
  the app open, 55 warm (MEASURED).

Part 3: scripts/android-session.py
----------------------------------
start/stop/status/install/launch/run/shell/xwd (its docstring has the
rules). The session root /Volumes/SteamARMAndroid/session is made once
(cp -c -R of $ANDROID_X86_ROOT, 0.6 s) and keeps the session's /data:
installed apps and their data (not $STATE/android/data/<pkg>, which is not
bound into it). Host state /tmp/lxrt-android-session-<uid> (sockets: short
paths); log $STATE/logs/android-<date>.log (this program and android-boot's
output). One session at a time: $STATE/android/session.json and a lock;
android-boot runs in a session of its own, with --exit-with the `run`
process, so a killed wrapper takes the boot with it. `run` ends on
SIGTERM/SIGINT/SIGHUP, when Weston is gone (the window closed) or when the
boot is.

not clicked; its Abrir path is run-app.sh's, whose dry runs are tested and

Not done, and why
-----------------
- arm64-v8a-only apps: Android's arm64 ART needs its heap below 4 GiB and
  macOS maps nothing there in an arm64 process (docs/ANDROID_RUNTIME_ARCHITECTURE.md,
  "The ART heap wall"). Disabled with that reason.
- 32-bit x86 apps: the display profile declares no 32-bit ABI (one zygote
  fewer); --abi32 starts zygote_secondary with a FEX that has
  patches/fex-lxrt-i386-bionic.patch, not measured end to end.
- Sound (no audio in the session: the audio HAL is passthrough without a
  PulseAudio socket unless --pulse), network (netd is a stand-in: none),
  camera, GPU (SwiftShader on the CPU).
- Clicks and keys from the Mac: the path is open to InputDispatcher for
  pointer motion (MEASURED); buttons and keys were not sent (see 5 above).
- Android's clock shows UTC (no persist.sys.timezone from the host).
- Uninstalling a card (android-pm.py) does not uninstall it inside the
  session root.
- The stand-in lmkd never answers LMK_GETKILLCNT: `dumpsys activity lmk`
  would wait (HYPOTHESIS from the source above).
