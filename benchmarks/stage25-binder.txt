Stage 25 -- Android binder in userspace under lxrun: servicemanager, service, a native service (2026-09-29)
=========================================================================================================

ZERO-VM. No virtual machine, no guest kernel, no FEX. Host: Mac mini M4,
16 GB, macOS 27.0. Base: 53432eb plus the stage-25 Android userspace work
(1e35b68, merged). Every Android program below is an unmodified Android 11
arm64 binary from the Waydroid LineageOS 18.1 root of
benchmarks/stage25-android-userspace.txt (/Volumes/SteamARMAndroid/root),
run by lxrun as a macOS process. Nothing was signed in to, no Google
component was downloaded, no Steam client was started. Other sessions ran
guests on the same Mac (a FEXServer started elsewhere was running); every
process below was started and stopped by this session, by its own PID, and
every binder hub it started left by itself when idle. Home paths are
written as ~. Labels: MEASURED, VERIFIED IN SOURCE, UPSTREAM DOCUMENTED,
HYPOTHESIS, UNKNOWN.

Result
------
MEASURED:
1. /dev/binder, /dev/hwbinder and /dev/vndbinder exist for every lxrun
   process, as a userspace driver: runtime/binder_hub.c (the driver's state
   in a host process, `lxrun --binder-hub <dir>`, started on demand) and
   runtime/binder.c (the guest's open/ioctl/mmap/poll/close/fork).
2. Android 11's own servicemanager runs as the context manager. Android's
   own clients work against it: `service list` ("Found 1 services: 0
   manager: [android.os.IServiceManager]"), `service check`, `service
   call`, `dumpsys -l`.
3. A native service in another process (tests/android/binder_service.c,
   raw ioctls) registers with servicemanager, is listed with its interface
   name, is called by `service call` with an int (41 -> 42) and with a file
   descriptor (it reads /system/etc/hosts through it: 56 bytes, byte sum
   3516, equal to the file on the Mac), and when it exits servicemanager's
   death notification removes it.
4. Real libbinder daemons register and serve from libbinder's own thread
   pool: idmap2d answers IIdmap2::getIdmapPath with
   "/data/resource-cache/product@overlay@Test.apk@idmap"; credstore
   registers and answers with an AIDL service-specific error ("Error
   creating default store": there is no identity-credential HAL).
5. vndservicemanager on /dev/vndbinder with `vndservice list`: a separate
   context. hwservicemanager becomes the /dev/hwbinder context manager but
   cannot set hwservicemanager.ready (no property service), and lshal never
   gets as far as opening /dev/hwbinder: the next wall is properties.
6. Costs: a sync round trip is 36-38 us to a looper parked in
   BINDER_WRITE_READ (libbinder's thread pool) and 46-55 us to a server that
   polls like servicemanager; the host floor for the same three-process
   relay over Unix sockets is 8-9 us. `service list` takes 60 ms median,
   `toybox true` 58 ms: process start-up, not binder, is the cost.
7. tests: tests/elf/run.sh BINDER_IPC (20 checks, two processes, raw ioctls
   against the Linux UAPI header) and BINDER_POOL; tests/android/run.sh
   15 passed + ART's expected failure. Full-suite numbers at the end.

Design (runtime/binder.h, docs/ANDROID_RUNTIME_ARCHITECTURE.md "Binder")
------------------------------------------------------------------------
- The hub: one per user, /tmp/lxrt-binder-<uid> (LXRT_BINDER_DIR), socket
  hub.sock 0600 in a 0700 directory; leaves 10 s after its last client
  (LXRT_BINDER_HUB_IDLE); logs user errors to hub.log, every transaction
  under LXRT_BINDER_LOG=1. Started by the first open with posix_spawn of
  lxrun itself (--binder-hub <dir> --daemon, POSIX_SPAWN_CLOEXEC_DEFAULT,
  stdio on /dev/null): that first process binds and listens, forks the real
  hub (setsid) and exits, so the hub is nobody's child and inherits no
  guest descriptor. Single-threaded; a thread that would sleep in
  BINDER_WRITE_READ is parked (its answer is not sent yet).
- State and semantics ported from drivers/android/binder.c (Linux 5.x):
  procs, threads, nodes, refs, descriptors (0 = context manager), work
  lists, transaction stacks, buffer allocator, death notifications. Checked
  afterwards line by line against Linux v5.10's binder.c (downloaded to the
  session scratch directory for reading only, GPL-2.0, not committed):
  binder_inc_node_nilocked, binder_dec_node_nilocked,
  binder_cleanup_ref_olocked, binder_inc_ref_olocked, binder_dec_ref_olocked,
  binder_translate_handle, binder_thread_release, binder_poll, the
  BR_SPAWN_LOOPER condition, the -ESRCH -> BR_DEAD_REPLY mapping, the FDA
  release: VERIFIED IN SOURCE, same logic.
- The guest's descriptor is its connection to the hub (the process
  channel): poll/epoll work on it unchanged. Doorbell bytes make it
  readable when work waits for a polling thread; every answer carries the
  count written and whether one should stay unread, and the runtime reads
  exactly up to that count. Each guest thread has its own channel (a
  socketpair handed to the hub with SCM_RIGHTS).
- BINDER_WRITE_READ sends the write bytes plus, per transaction, what the
  kernel copies from the sender (data, offsets, scatter-gather buffers,
  the descriptors named by FD/FDA objects, by SCM_RIGHTS). The receive
  buffer is a file: read-only for the guest, read-write in the hub, which
  copies each transaction into it as the kernel does; the runtime writes
  installed descriptor numbers through its own read-write view.

--------------
R0. Before (HEAD runtime plus the stage-25 userspace work, LXRT_KEEP_X18=1

      Binder driver '/dev/binder' could not be opened.  Terminating.
      libc: Fatal signal 6 (SIGABRT) ...   rc=1

R1. First BINDER_IPC run: 17 ok, 3 MAL.
    - "a second context manager is refused (EBUSY)": EBADF. Cause: the
      runtime's open skipped the hello when the hub was already listening
      (only the spawn path said hello); the hub dropped the connection on
      its first message. Fixed in the open loop.
    - "20 oneway transactions arrived, in order": 11. Not a driver bug:
      oneway calls to one node are delivered one at a time (the next one
      only after BC_FREE_BUFFER of the previous), so a sync call can
      overtake the queue, as on Linux. The test now asks until all 20
      arrived: 20, in order, after 11 sync calls.
    - the client's exit status followed from the second.

R12. Review. A read-only review by Codex (gpt-6-sol, effort high) of
    binder.c, binder_hub.c and the hooks reported 8 findings. Fixed:
    - munmap of the receive buffer left the hub allocating there
      (Linux: binder_vma_close, then -ESRCH/"no vma" -> BR_DEAD_REPLY);
      the runtime now tells the hub. Test: after munmap, a call's reply
      cannot be delivered, BR_DEAD_REPLY.
    - installing descriptors into the buffer raced another thread's munmap:
      serialised.
    - dup3: a bad oldfd dropped newfd's module state before failing;
      O_CLOEXEC was ignored (Darwin's dup2 clears it); other flags were not
      EINVAL. All lxrun guests, not only binder.
    - TF_CLEAR_BUF (Linux 5.11) was not honoured: the buffer is now zeroed
      when freed. Test added.
    - a 17th receive buffer in one process was untracked: refused.
    Kept, with the source as evidence: "the next oneway work after
    BC_FREE_BUFFER should go to thread->todo" and "a death notice for an
    already dead node should go to the looper's thread->todo": in Linux
    v5.10 both go to proc->todo (binder.c lines 3565 and 3913 of v5.10).
    BINDER_IPC after the fixes: 20/20, 3 runs; BINDER_POOL 3/3;
    tests/android 14 passed + 1 expected failure.

What servicemanager still needs
-------------------------------
Nothing to run and serve (MEASURED above). Around it, for Android as a
whole: a property service (hwservicemanager.ready, HIDL, setprop, ashmem's
choice of memfd), init's start order, per-app uids (every process has the
Mac's uid 501), SELinux labels (the image's servicemanager has its checks
compiled out; the driver reports LXRT_BINDER_SECCTX, default
u:r:unlabeled:s0), and ART's heap (docs/ANDROID_RUNTIME_ARCHITECTURE.md).
