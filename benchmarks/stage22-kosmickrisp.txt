Stage 22 -- KosmicKrisp as a second Vulkan driver; present modes reported
(2026-09-29)
=========================================================================

Host: Mac mini M4, 16 GB, macOS 27.0 (26A428). Homebrew mesa 26.2.3
(KosmicKrisp), molten-vk 1.4.2, vulkan-headers 1.4.357.0. Display 1920x1080
at 165 Hz. Other SteamARM guests (a native arm64 Steam client, i386 tests)
were running from other worktrees during every measurement below, so the
fps figures carry that load.

ZERO-VM: unchanged. The driver is a Mach-O dylib called in-process through
the runtime's host bridge, exactly as MoltenVK is.

Summary
-------
- STEAMARM_VK_ICD selects the driver the ELF Vulkan shim loads. Unset or
  "moltenvk": MoltenVK, as before. "kosmickrisp": Mesa's KosmicKrisp. A
  value starting with "/": that dylib. A driver that cannot be used falls
  back to MoltenVK and prints one line on stderr.
- KosmicKrisp works through the shim with no Khronos loader: aarch64, x86-64
  and i386 guests (FEX thunks) create an instance and a device, submit and
  read back, and present to an X window. D3D11 (DXVK) and D3D12
  (VKD3D-Proton) probes under Proton Experimental run on it once the shim
  reports fillModeNonSolid (commit 8a716c9; without it DXVK rejects the
  adapter). MEASURED, below.
- The default path is unchanged: every MoltenVK probe passes as before.
- The shim logs each swapchain's present mode (requested, and what is passed
  to the driver) with LXRT_VK_DEBUG=1; LXRT_VK_PRESENT_MODE=FIFO|IMMEDIATE
  overrides it when the surface offers that mode.
- Not tested: Steam's launch path (pressure-vessel) with STEAMARM_VK_ICD, any
  real game, D3D9, 32-bit D3D on KosmicKrisp. See "Not done".

1. What the shim does (VERIFIED IN SOURCE, this branch)
-------------------------------------------------------
shim/gen.py -> shim/vulkan_shim.c, constructor lxrt_vk_init:
  - STEAMARM_VK_ICD and LXRT_VK_DEBUG are read with the HOST's getenv
    (lxrt_host_dlsym(RTLD_DEFAULT, "getenv")): the environment the runtime
    was started or re-executed with (runtime/process.c:137), readable before
    the guest's libc is initialised. A variable a process sets for itself
    after it started is not seen.
  - kosmickrisp: /opt/homebrew/lib/libvulkan_kosmickrisp.dylib, then
    /usr/local/lib/libvulkan_kosmickrisp.dylib.
  - bind(): a dylib that exports vkCreateInstance (MoltenVK) is bound by name
    as before. One with vk_icdGetInstanceProcAddr and no vkCreateInstance
    (Mesa) is bound in ICD mode: vk_icdNegotiateLoaderICDInterfaceVersion(7),
    then every slot from gipa(NULL, name); vk_icdGetInstanceProcAddr's slot
    is the driver's gipa; vkEnumerate{Instance,Device}LayerProperties, which
    the Khronos loader implements, report zero layers if the driver lacks
    them.
  - lxrt_vk_icd_fill(instance), called after every successful
    vkCreateInstance (shim/wsi.c): each slot still empty is filled once from
    gipa(instance, name), under a lock.
  - lxrt_vk_missing(name): in ICD mode vkGetInstanceProcAddr /
    vkGetDeviceProcAddr answer NULL for a driver entry point whose slot is
    empty (the loader's behaviour) instead of a thunk that traps at brk #2.
    Entry points the shim implements itself (X11 surfaces, transform
    feedback) are not driver slots and stay available.
  - Messages: "[shim] vk driver requested=X effective=Y (reason)" on a
    fallback, or always with LXRT_VK_DEBUG=1 (reason "exports" or "icd").
    Written with a raw Linux write(2): no libc needed in the constructor.
  - The binary contains the literal "STEAMARM_VK_ICD" (strings: 1 match).
shim/wsi.c, ICD mode only: the instance extension list keeps the driver's
  own VK_KHR_xcb_surface / VK_KHR_xlib_surface (KosmicKrisp lists them) instead
  of adding duplicates, and drops VK_EXT_acquire_xlib_display (it would hand
  the driver's host X11 code a guest Display). X11 surfaces are still the
  shim's (remote CAMetalLayer, stage12).
shim/present.c: vkCreateSwapchainKHR (section 6).
shim/features.c: fillModeNonSolid spoofed like geometryShader (section 5).
Nothing touches driverVersion or any VkPhysicalDeviceProperties field for
display; the values below are the drivers' own.

2. Dispatchable handles without a loader (the crux)
---------------------------------------------------
UPSTREAM DOCUMENTED / VERIFIED IN SOURCE (Mesa main, fetched 2026-09-29
through the gitlab API -- main, not the 26.2.3 tag):
  src/vulkan/runtime/vk_object.h:43-44  struct vk_object_base {
                                           VK_LOADER_DATA _loader_data; ...
  src/vulkan/runtime/vk_object.c:39,52  _loader_data.loaderMagic = ICD_LOADER_MAGIC
  src/vulkan/runtime/vk_instance.c:297-365  vk_instance_get_proc_addr: the
      global names for any instance; with an instance, instance entry
      points, then physical-device and device TRAMPOLINES, each only if
      enabled by the instance's apiVersion / extensions
  src/vulkan/util/vk_dispatch_trampolines_gen.py:116-127  a device
      trampoline dispatches through vk_device->dispatch_table or
      vk_object_base->device->dispatch_table -- never through _loader_data
Khronos vk_icd.h: ICD_LOADER_MAGIC 0x01CDC0DE, set_loader_magic_value().
The Khronos loader overwrites that first word with its own dispatch pointer;
nothing in the driver reads it.

MEASURED (host probe, a Mach-O C program dlopen'ing the dylib, no loader):
  KosmicKrisp: negotiate -> 0, version 7. First word of VkInstance,
  VkPhysicalDevice, VkDevice, VkQueue, VkCommandBuffer = 0x1cdc0de, before
  and after a vkCmdFillBuffer + vkQueueSubmit + fence wait; readback
  0xcafef00d. gipa gives vkCmdFillBuffer 0x...6e8f4 (trampoline) and
  vkGetDeviceProcAddr gives 0x...7131c (the driver's own) -- both work.
  MoltenVK, same probe: negotiate -> version 5, first words 0x1cdc0de,
  readback ok.
So the shim needs no dispatch pointer in the objects: it calls the driver
through its own global table, as it always did for MoltenVK.

MEASURED (host probe over shim/entrypoints.txt, 431 names):
  gipa(NULL, name): 6 resolve (the globals and vk_icd*).
  gipa(instance at apiVersion 1.4 with every instance extension but the X11
  ones): 414 resolve, 17 NULL: vk_icdGetInstanceProcAddr (the shim fills
  it), vkEnumerateInstanceLayerProperties (the shim's zero-layer version),
  vkCreateHeadlessSurfaceEXT, and 14 *MVK entry points.
  Two instances: 0 of 431 pointers differ.
  A 1.0 instance without extensions: NULL for vkCmdBeginRendering,
  vkQueueSubmit2, vkGetPhysicalDeviceProperties2, vkCreateMetalSurfaceEXT --
  hence "fill what is still empty after EVERY vkCreateInstance", not only
  after the first.

6. Present modes (MEASURED unless marked)
-----------------------------------------
Offered by the surface (vk_x11_present): MoltenVK "FIFO IMMEDIATE",
KosmicKrisp "IMMEDIATE FIFO". Neither offers MAILBOX or FIFO_RELAXED.
Requested by the probes (shim log):
  d3d11 (DXVK, Present(sc, 0, 0)): IMMEDIATE on both drivers.
  d3d12 (VKD3D-Proton, Present(0,0)): FIFO on MoltenVK, IMMEDIATE on
    KosmicKrisp, two swapchains each. Why it differs: UNKNOWN (HYPOTHESIS:
    MoltenVK exposes VK_KHR_present_wait / present_id and KosmicKrisp does
    not, audit "capabilities").
vk_x11_present, 570 frames each:
  MoltenVK FIFO       median 6.047 ms, mean 6.083
  MoltenVK IMMEDIATE  median 6.039 ms, mean 4.858
  KosmicKrisp FIFO    median 6.070 ms, mean 6.126
  KosmicKrisp IMMEDIATE median 6.070 ms, mean 6.061
  LXRT_VK_PRESENT_MODE=IMMEDIATE on a FIFO request:
    MoltenVK "requested=FIFO passed=IMMEDIATE LXRT_VK_PRESENT_MODE=immediate
    -> 0", median 6.060 ms, mean 6.061; KosmicKrisp median 6.010 ms, mean
    4.637.
  LXRT_VK_PRESENT_MODE=mailbox: "passed=FIFO ... (LXRT_VK_PRESENT_MODE not
    understood: FIFO or IMMEDIATE)".
  IMMEDIATE never moved the median off the 165 Hz refresh (6.06 ms); the
  mean dropped below it in some runs and not in others, on both drivers.
  Whether IMMEDIATE tears or unlocks through the cross-process layer is
  still UNKNOWN; this probe waits for its fence every frame, so it cannot
  run ahead of acquire. The "surface does not offer it" branch was not
  exercised (both modes are always offered on Metal).

7. The steam root's shim: swap protocol (MEASURED)
--------------------------------------------------
The x86 probes load the aarch64 shim from the Steam root, not from the
worktree. Two copies are used: usr/lib64/libvulkan.so.1 (FEX-gb from
/tmp/lxrt-root has no RPATH -- the copy tests/elf/run_vk_device.sh and
tests/win reach) and usr/lib/lxrt-emu/libvulkan.so.1 (the Steam root's FEX
has RPATH /usr/lib/lxrt-emu). A first swap of only lxrt-emu left the probes
on the original shim (no "[shim] vk driver" line, MoltenVK despite
STEAMARM_VK_ICD) -- that is how the second copy was found.
Each session: sha256 of both recorded, both copied to a backup outside the
root, originals renamed aside (running guests keep their inode), the test
build copied in by rename, probes run, test build removed, originals renamed
back, sha256 checked. Seven sessions (x86 vk_device twice -- the first
swapped lxrt-emu only --, x86 X11 present, vulkaninfo, D3D, the uncommitted
fillModeNonSolid experiment, final); every restore printed
  46c9c0071fd19d2f6d70015d1f45c528faf4369a4e5ff0b14276eac00a300636 (before)
  46c9c0071fd19d2f6d70015d1f45c528faf4369a4e5ff0b14276eac00a300636 (after)
for every file swapped. No Steam client was running from that root (lsof: no
process had the shim open before the first swap).
