Stage 52 -- Presenting without waiting for the display (IMMEDIATE and
MAILBOX swapchains)
Date: 2026-10-02. Apple M4, macOS 27, display 1920x1080 at 165 Hz. Zero VM.
Follows stage 51 (section 8a): Counter-Strike 2 stopped at 82.5 frames a
second, half the display's rate.

1. WHAT THE LAYER DOES
  A guest's swapchain presents to a CAMetalLayer shown by another process
  (CAContext, runtime/remote_layer.m). tests/elf/vk_x11_present.c, a clear
  and a present per frame, 570 frames, median frame time:
                         FIFO       IMMEDIATE
    MoltenVK 1.4.2       6.071 ms   6.064 ms
    KosmicKrisp 26.2.4   6.059 ms   6.064 ms
  165 frames a second either way: the driver sets displaySyncEnabled = NO
  for IMMEDIATE and the window server still takes one drawable per refresh.
  CAMetalLayer nextDrawable is the only way to get one and it blocks (Mesa's
  WSI: "we might block for up to 1 second"). So a frame that takes 8.8 ms
  waits for the second refresh: 12.1 ms, 82.5 fps, and the game's
  vkAcquireNextImageKHR took 3.3 ms on average.

2. THE MAILBOX (shim/mailbox.c)
  For a swapchain created with IMMEDIATE or MAILBOX (and not scaled): the
  game gets images of the shim's own and its acquire returns at once; a
  thread acquires the driver's image; the game's present copies its image
  into the driver's and presents it if one is ready, and drops the frame if
  not. The driver's acquire and present never overlap; everything on the
  queue is done on the game's threads, the acquire's own batch and the
  game's submits taking turns (DXVK acquires and submits on different
  threads). LXRT_VK_MAILBOX=0 turns it off.
