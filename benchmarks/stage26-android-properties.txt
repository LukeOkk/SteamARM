Stage 26 -- Android system properties under lxrun: a property service with no init and no VM (2026-09-29)
======================================================================================================

ZERO-VM. No virtual machine, no guest kernel, no FEX. Host: Mac mini M4,
16 GB, macOS 27.0. Base: 3651c06 (stage 25, binder in userspace). Every
Android program below is an unmodified Android 11 arm64 binary from the
Waydroid LineageOS 18.1 root of benchmarks/stage25-android-userspace.txt
(/Volumes/SteamARMAndroid/root), run by lxrun as a macOS process. Nothing
was signed in to, nothing was downloaded into the root, no Google component
was fetched, no Steam client was started. Other sessions ran guests on the
same Mac (a FEXServer and another agent's guests were running); every
process below was started by this session and stopped by its own PID or
left by itself (the property services and binder hubs, when idle). Home
paths are written as ~. Labels: MEASURED, VERIFIED IN SOURCE, UPSTREAM
DOCUMENTED, HYPOTHESIS, UNKNOWN.

Result
------
MEASURED:
1. /dev/__properties__ exists for every lxrun guest of an Android root: a
   host process, `lxrun --property-service <dir> <root>` (runtime/
   propsvc.c), builds property_info and one bionic prop_area per SELinux
   context from the image's own property_contexts and .prop files, as
   Android 11's init does, and serves /dev/socket/property_service. The
   runtime (runtime/props.c) maps the two guest paths to the service's
   private directory, starts the service on demand, and reports the area
   files as root-owned, which bionic requires.
2. bionic reads them unmodified: getprop lists 224 properties, every
   ro.build.* value of /system/build.prop among them (23 of 23);
   ro.build.fingerprint is derived from the image's own values as init
   derives it (the image sets none).
3. setprop in one guest, getprop in another; ro.* written once (the image's
   values cannot be changed, a new ro.* takes its first value only); the
   property_contexts types are checked (an int refuses "abc"); ctl.* is
   refused and logged (there is no init); persist.* is stored in init's
   PersistentProperties protobuf and restored by a fresh boot.
4. __system_property_wait works across processes: a bionic program linked
   against the image's own libc.so waits for a property that does not exist
   yet and wakes when another guest's setprop creates and then changes it.
   The wake is the service's __ulock_wake on the shared file mapping
   reaching the guest's FUTEX_WAIT: 1000 of 1000 changes seen, median
   18.6 us after the setter's send when back to back, 100 us when 5 ms
   apart.
5. hwservicemanager now sets hwservicemanager.ready through the property
   service, and lshal lists hwservicemanager's 5 interfaces. Three HIDL HALs
   of the image register with it and are listed: android.hidl.allocator@1.0
   (IAllocator/ashmem), android.hardware.configstore@1.1
   (ISurfaceFlingerConfigs) and android.hardware.memtrack@1.0 (IMemtrack,
   passthrough to memtrack.waydroid.so). lshal exits 72
   (DUMP_BINDERIZED_ERROR | IO_ERROR): its thread and client columns read
   /dev/binderfs/binder_logs/proc/<pid>, the binder driver's debug state,
   which the userspace driver does not publish.
6. No start-up cost: `toybox true` median 38.6 ms with properties, 38.7 ms
   with the service switched off. The first bionic process of a root boots
   the service (9-13 ms of the service's time; 57 ms for that process).
7. tests/android/run.sh: 29 passed + ART's expected failure (was 15 + 1).
   Full-suite numbers at the end.

Design (runtime/props.h, docs/ANDROID_RUNTIME_ARCHITECTURE.md "Properties")
---------------------------------------------------------------------------
- One property state per Android root: LXRT_PROPERTY_DIR, else
  /tmp/lxrt-props-<uid>-<hash of the root's real path>, private (mode 0700,
  the user's own; otherwise no property service is offered, as for the
  binder hub). In it: __properties__/ (property_info 0444, 160 context
  files and properties_serial, 128 KiB each, sparse: 44 KB on disk),
  property_service (the socket), service.lock, spawn.lock, service.pid,
  service.log.
- The service: a boot builds everything in __properties__.new and renames
  it into place, so no guest sees half of it; a service started again
  finds the areas and adopts them (they are the state; nothing is reset).
  It leaves after LXRT_PROPERTY_IDLE seconds without a setprop (default
  60; 0 never), or when its directory is removed. Removing the directory
  is the "reboot" of that root's properties.
- Guests: /dev/__properties__[/...] and /dev/socket/property_service are
  translated to that directory. The first process that finds no
  property_info starts the service (posix_spawn of lxrun itself; its first
  process boots, binds, forks the service and exits, so the areas exist
  when the spawner's waitpid returns); a connect() to the socket that finds
  no listener starts it and retries once. fstat/stat/statx of the area
  files answer uid 0 and gid 0 (only in a process that has looked at
  /dev/__properties__, and only when the device number matches).
- Writes: the service maps the area files read-write MAP_SHARED; guests map
  them read-only MAP_SHARED (a real host mapping: 128 KiB is whole 16 KiB
  pages, and dispatch.c registers it as shared for futexes). Updates follow
  Update/Add above; wakes are __ulock_wake(UL_COMPARE_AND_WAIT_SHARED |
  ULF_WAKE_ALL) on the serial words, the queue runtime/futex_ops.c parks a
  guest's non-private FUTEX_WAIT on in a shared mapping.
- Boot values: LXRT_PROPERTY_BOOTARGS stands for the kernel command line
  (androidboot.x=y -> ro.boot.x; empty by default; "qemu" is not honoured),
  then init's ExportKernelBootProps defaults (ro.hardware=unknown,
  ro.bootmode=unknown, ...), the .prop files in init's order, the derived
  properties, ro.property_service.version=2, /data/local.prop (debuggable
  builds), the persistent properties, ro.persistent_properties.ready=true.
  Nothing else is invented: no certification-related property is set or
  changed; ro.build.fingerprint is the image's own derivation (userdebug,
  test-keys).
- Persistent file: LXRT_PROPERTY_PERSIST, else the guest's own
  /data/property/persistent_properties in the root (init's path and
  format), so persist.* survives with the rest of the root's /data.
- Not done, stated: no SELinux (CheckMacPerms and CanReadProperty are not
  applied; every area is readable), no init to act on ctl.* (refused,
  PROP_ERROR_HANDLE_CONTROL_MESSAGE, logged), no property triggers ("on
  property:" actions), no vendor_load_properties hook, restorecon is a
  no-op (selinux.restorecon_recursive is set at once), sys.powerctl only
  logged. Every guest is the Mac user: ro.* write-once is the protocol's
  rule, not a security boundary (a guest could chmod the area files).

R12. Review. A read-only review by Codex (gpt-6-sol, effort high) of
    props.c, propsvc.c and the hooks, against the AOSP sources above,
    reported 6 findings; it found the prop_area/prop_bt/prop_info layout,
    the long-value offsets and the update fences equal to bionic's. All 6
    fixed (commit "property service review fixes"), each checked against a
    small synthetic root on the host:

      climbing out of the root would have put the persistent file outside
      it. Now resolved like a chroot: with /data ->
      ../../../../../../tmp/outside the file is
      <root>/tmp/outside/property/persistent_properties, nothing outside.

      (rename over a non-empty directory); an area with an offset past its
      end would have been followed. Now the areas are validated before
      adoption and bad state is set aside: "cannot adopt ...; moved to
      __properties__.bad-<pid>, booting again" in both cases (a root
      children offset of 128 KiB - 128 written into default_prop's area:
      "an offset points outside the area").

      kept the file; init deletes it and applies nothing. Now the same
      ("Could not parse protobuf (deleted)"). init's legacy
      /data/property/persist.* files are migrated when there is no
      protobuf (a persist.steamarm.legacy file became a record and a
      property, the file went).
    - Derived ro.product.brand and the fingerprint truncated a long ro.*
      value (92 and 1024 bytes): a 120-byte ro.product.product.brand now
      reaches ro.product.brand and ro.build.fingerprint whole.
    - A service leaving when idle could, with a client that connects and
      sends nothing, drain for longer than the 5 s others waited: the drain
      is capped at 2 s in all and the waits are 10 s.
    After the fixes: property_info still byte-identical (R3), the battery
    29 passed + 1 expected failure.

What the native services need next
----------------------------------
- init, or its part that matters here: a start order (logd, servicemanager,
  hwservicemanager, vndservicemanager, the HALs), restarts, and property
  triggers ("on property:..." actions, e.g. hwservicemanager.rc's
  "onrestart setprop hwservicemanager.ready false"). The property service
  has no trigger hook yet.
- Shared memory across processes: HALs hand ashmem/memfd buffers to their
  clients (the allocator above is one); lxrun's memfd sealing holds within
  one process (docs/LEPTON_REUSE_ANALYSIS.md 7). Now that ro.vndk.version
  is set (30), libcutils' ashmem may take its memfd path (HYPOTHESIS, not
  exercised: no client of IAllocator was run).
- The binder driver's debug state (/dev/binderfs/binder_logs) for lshal's
  thread and client columns: cosmetic.
- For anything Java, the ART heap (docs/ANDROID_RUNTIME_ARCHITECTURE.md)
  is unchanged and still first.
