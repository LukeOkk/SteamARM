# FEX_REUSE_ANALYSIS

> **SUPERSEDED — VM-era provenance.** Audited while FEX was built in the
> Fedora VM. The FEX pin is unchanged (`08f451d3b`,
> `scripts/build-fex-host.sh:74`), and FEX is now built on the Mac with no
> VM (stage 9), with 8 host patches (`scripts/build-fex-host.sh:79`) and 3
> thunk-generator patches in `patches/`. The source analysis below still
> applies to that commit.

**FEX version audited:** `FEX-2609-113-g08f451d3b` — commit `08f451d3b` ("Merge pull request #5980 from Plagman/plagman/maxrwsize_mr"), tag FEX-2609 plus 113 commits. This is the exact commit built on the project's Linux guest (`~/FEX` on the Fedora 43 aarch64 VM; `git describe --tags`) and the commit checked out on the host for this audit. Date: 2026-09-25.

**Evidence classes.** MEASURED — run in this project, output recorded under `benchmarks/`. VERIFIED IN SOURCE — the cited file:line exists at this commit and says what is claimed. UPSTREAM DOCUMENTED — `docs/` or an in-tree comment. HYPOTHESIS — plausible, not confirmed. UNKNOWN — not determinable from the source; needs a measurement. Nothing below is upgraded from HYPOTHESIS to fact without a measurement.

**How this was produced.** Five parallel readers over the source tree (syscalls; memory/JIT/threads; thunks/VDSO; Wine/ARM64EC/frontend; signals/TLS/cache/i386/config), each finding then re-checked by a skeptical verifier against the cited lines (12 of 76 findings corrected; the corrections are applied here). Runtime-side answers come from this project's own measurements.

**How the runtime relates to FEX (the frame for everything below).** FEX is not ported. The unmodified Linux aarch64 build of FEX (two small patches, one build flag) runs as a guest ELF under the project's runtime (`runtime/`, "lxrt"), which is FEX's kernel: every Linux syscall FEX issues ends in `runtime/dispatch.c`, every `svc` in FEX's text is rewritten at load, and Darwin never sees Linux ABI. So "reusable on Darwin" below means "works when the runtime provides the Linux semantics it needs", and "adapter" usually means runtime work, not FEX work.

## Answers

**1. Exact FEX version.** `FEX-2609-113-g08f451d3b`, commit `08f451d3b` (VERIFIED: `git describe --tags` on the guest tree and on the host clone). Built on the Fedora 43 aarch64 guest (kernel 6.17.1): `Build/` Release and `Build-dbg/` RelWithDebInfo, `-DBUILD_FEXCONFIG=False`, and since 2026-09-25 `-DCMAKE_C_FLAGS=-ffixed-x18 -DCMAKE_CXX_FLAGS=-ffixed-x18`. Installed as `/tmp/lxrt-root/usr/bin/{FEX,FEXServer,FEXGetConfig,FEX-dbg,FEXServer-dbg}`. `BUILD_THUNKS` and `BUILD_STEAM_SUPPORT` are off in this build (VERIFIED: CMake cache on the guest has no thunk targets; `STEAM_COMPAT_*` handling is compiled out).

**2. Local patches.** Two, plus one build flag — all small, all answered per the brief's five questions:
- `patches/fex-lxrt-wx.patch` + `patches/LxrtJit.h` (Dispatcher.cpp, JIT.cpp, Utils/ArchHelpers/Arm64.cpp): a three-line `JitWriteScope` around the emitter and the two code-buffer memcpys, issuing private syscall `0x4C580020` (per-thread write/execute flip + rescan of the emitted range). Why: Darwin has no RWX; a MAP_JIT flip issued inside a signal handler does not survive the handler's return (MEASURED). Linux dependency removed: none — it removes a *Darwin* constraint. Upstreamable: as a host-platform hook (`FEXCore::Allocator` W^X callbacks), plausible. External alternative: none (the flip must come from the writing thread). Maintenance: ~40 lines; rebased once already. Not yet covering: the unaligned backpatcher's stores, seccomp's BPF JIT, thunk trampolines.
- `patches/fex-lxrt-x18.patch` (Arm64Emitter.cpp:76-92): removes r18 from `x64::RA`, `PreserveAll_Dynamic`, `NotPreserved_Dynamic`. Why: Darwin zeroes x18 on every exception return (MEASURED, `benchmarks/stage5-x18.txt`). Linux dependency removed: none (platform-register semantics). Upstreamable: yes, mirroring the ARM64EC branch that already excludes r18. Cost of one fewer dynamic register: not measured. Maintenance: 12 lines.
- `-ffixed-x18` for FEX's own C++ (2271 sites before; 0 after, MEASURED with llvm-objdump).

**3. How Steam enters FEX today.** In the VM: `run.sh ./ubuntu12_32/steam` execs an i386 ELF; the guest kernel's binfmt_misc registration (`Data/binfmts/FEX-x86_64.conf.in`, `POCF` flags, `preserve argv0`) hands it to `FEX`; MEASURED live with ftrace: `steam` (pid 923), six `steamwebhelper`, the launcher service, all FEX processes (`benchmarks/stage6-steam-gap.txt`). Under the runtime: no kernel, no binfmt — the runtime is started as `lxrun FEX <x86 program>`; FEX's own re-exec of children (`execveat(/proc/self/exe)`) is mapped by the runtime to a fresh `lxrun` (MEASURED: `steamwebhelper` and `bash` children). The Steam client itself has not entered FEX under the runtime: it is an i386 PIE that must live below 4 GiB.

**4. How FEX handles syscalls.** x86 `syscall`/`int 0x80` → IR `_Syscall` → `SyscallHandler::HandleSyscall` (`Syscalls.cpp:879-895`) → the x64 or x32 `Definitions` table (VERIFIED). ≈241 x64 entries are passthrough templates (`Passthrough.cpp`: inline `svc #0`, x8 = Linux arm64 number, raw -errno in x0); ≈114 are FEX-implemented (memory via its allocators + VMA tracking, threads, signals, execve, openat with the rootfs overlay, /proc emulation, seccomp in userspace, ioctl translation for 32-bit). The x32 table translates structures (`x32/Types.h`) and numbers (≈203 passthrough vs ≈221 emulated).

**5. Where a guest syscall ends.** In the Linux kernel, through three channels: the inline `svc #0` templates, glibc's `::syscall(SYS_*)` (~33 files), and ordinary glibc wrappers (VERIFIED). Under the runtime all three end in the same place: the runtime's loader rewrites every `svc #0` in FEX's text and in the guest glibc/libstdc++ into a branch to a trampoline that reaches `lxrt_dispatch()` (`runtime/dispatch.c`) and returns the Linux result. MEASURED costs: rewritten svc → dispatcher → real Darwin syscall 68.1 ns; → userspace implementation 0.9 ns; native Darwin syscall 114.2 ns; SIGTRAP interception 2794 ns; Mach exception 6317 ns. One dispatcher serves both the ARM64 fast path and FEX (the brief's requirement).

**6. What depends directly on the Linux kernel.** Everything under `Source/Tools/LinuxEmulation` — by design it *is* the Linux backend. The load-bearing dependencies, each with its runtime status: 4 KiB pages (`FEX_PAGE_SIZE` constexpr; runtime sub-page layer, not exact for PROT_NONE guards); MAP_FIXED_NOREPLACE/EEXIST (implemented, guest-granular since today); mremap (implemented, 22/22); MADV_DONTNEED zero-fill (implemented); memfd + seals (implemented); openat2 RESOLVE_IN_ROOT (implemented); execveat + `/proc/self/exe` (implemented); futex incl. requeue ops (implemented); 64 Linux signals with the Linux `sigcontext`/fpsimd layout (implemented; **esr_context not fabricated**); `hlt` → SIGILL (works); SIGBUS BUS_ADRALN for unaligned atomics (UNKNOWN on XNU); clone/fork/per-thread exit (implemented); uname release gating (the runtime reports `6.6.0-lxrt`: gates ≤ 6.6 open, 6.8/6.10 closed — VERIFIED); prctl extras (TSO, MDWE, VMA names, shadow stack — all degrade cleanly); the low 4 GiB for i386 and ET_EXEC (**cannot be provided**, `__PAGEZERO`).

**7. Can that backend be replaced by the Darwin dispatcher?** It already is — without touching FEX's syscall layer, because FEX stays a Linux aarch64 program and the runtime is its kernel (strategy A). The only OS-neutral seam in FEX is `FEXCore::HLE::SyscallHandler` (VERIFIED); using it for a native Darwin FEX would mean re-implementing all of LinuxEmulation as a Darwin backend — a fork, rejected under the brief's preference order. What strategy A costs: every FEX host syscall pays the rewritten-svc path, and every Linux ABI detail FEX relies on has to be right in the runtime; `benchmarks/stage5-fex.txt` and `stage6-steam-gap.txt` are the ledger of what that took so far.

**8. How the Vulkan thunks of this version work.** Guest side: `libvulkan-guest.so` (x86, overlaying `libvulkan.so.1` via `ThunksDB.json`) turns each `vk*` call into `0F 3F` + a SHA256 of "libvulkan:vkXxx" plus packed arguments; FEX's decoder reserves that opcode; the JIT calls the host function registered for the hash (VERIFIED). Host side: `libvulkan-host.so` is a Linux aarch64 ELF that FEX `dlopen`s (`Thunks.cpp:212-260`); its generated `fexldr_init_libvulkan` `dlopen`s the real `libvulkan.so.1` and binds each function with `dlsym(RTLD_DEFAULT, …)` (`gen.cpp:782-802`, `Host.h:666-668`). Handles are opaque; non-dispatchable handles are `uint64` on both ABIs; `VkAllocationCallbacks` are opaque and always passed as `nullptr` to the host; the 64-bit path repacks nothing except platform structs (xcb/xlib connections through `X11Manager`); callbacks (debug messengers) go through RWX trampolines (`Thunks.cpp:43-66, 289-339`). 32-bit Vulkan thunks are not built at this commit.

**9. Can they connect to MoltenVK, and where is the ELF/Mach-O boundary?** Yes, in principle, and the boundary is exactly the `dlopen("libvulkan.so.1")` inside `fexldr_init_libvulkan`: under the runtime that dlopen is served by the guest ld.so and resolves to the project's **ELF shim** `libvulkan.so.1`, which forwards to MoltenVK (a Mach-O dylib) through the runtime's direct guest→host call (MEASURED 0.8 ns; Fedora's unmodified `vulkaninfo` and the triangle/swapchain tests run on MoltenVK today). So the chain is guest x86 → OP_THUNK → `libvulkan-host.so` (Linux ELF) → ELF shim → MoltenVK → Metal, with no RPC and no serialisation. What is not yet done: building the thunk artifacts (`BUILD_THUNKS`, needs libclang/LLVM/OpenSSL and an x86 cross toolchain on the Linux guest), the RWX trampoline pool (needs the W^X patch extended), and the `dlsym(RTLD_DEFAULT)` binding requiring the shim's symbols to be global in the guest link map (HYPOTHESIS: `RTLD_GLOBAL` in the generated loader makes this hold).

**10. Which thunk parts presuppose Linux.** The display-server surfaces (xcb/xlib/wayland platform macros, `X11Manager` dlopening host `libxcb`/`libX11`, custom repacking of connection/display pointers), `VK_KHR_external_memory_fd` and DRM format modifiers, the RWX trampoline pool, jemalloc_glibc interposition, and every non-Vulkan thunk (GL/EGL via GLX, wayland-client, drm ioctls, ALSA, CUDA). The Metal surface must come from the shim (the runtime already creates a `CAMetalLayer` surface for aarch64 guests).

**11. How VDSO thunking works.** `libVDSO-guest.so` is a tiny x86 ELF (soname `linux-vdso.so.1`) whose `__vdso_clock_gettime`, `gettimeofday`, `time`, `clock_getres`, `getcpu`, `getrandom` are thunks; FEX maps it into the guest (at 4 KiB hints with `MAP_FIXED_NOREPLACE|MAP_SHARED`) and, on the host side, parses the *host* vDSO from `getauxval(AT_SYSINFO_EHDR)` for `__kernel_clock_gettime` etc., falling back to libc when absent (`VDSO_Emulation.cpp:486-560, 788-882`, VERIFIED). It also supplies the guest's `__kernel_rt_sigreturn` stubs.

**12. Can it serve `clock_gettime`?** Yes. Under the runtime the auxv has no `AT_SYSINFO_EHDR`, so FEX takes the libc fallback: guest `clock_gettime` → thunk → host glibc → rewritten `svc` → the dispatcher's userspace clock (MEASURED 14.7 ns per call for an aarch64 guest; the x86 thunk path adds the OP_THUNK transition, not measured). A synthetic aarch64 vDSO ELF exposed through `AT_SYSINFO_EHDR` would remove the svc round-trip — HYPOTHESIS; measure the thunk path first, then decide (Milestone 6).

**13. How i386 support works.** `Is64BitMode` from the ELF class selects the x32 handler (`FEXInterpreter.cpp:493, 558-559`): compat syscall numbers and struct layouts (`x32/Types.h`), ioctl translation tables, 32-bit signal frames, `set_thread_area`/LDT emulation (pure `CpuState`), and the 32-bit allocator. Guest pointers are 32-bit and identity-mapped: host address == guest address.

**14. How the 32-bit allocator works.** `MemAllocator32Bit` keeps a `std::bitset<0x100000>` of 4 KiB pages over the whole 32-bit VA, reserves the first 16 pages and the top page, searches top-down and probes with `mmap(addr, …, MAP_FIXED_NOREPLACE)`, retrying on EEXIST (`LinuxAllocator.cpp:23-227`). It needs [0x10000, 0xFFFFF000) of the host process — which Darwin's `__PAGEZERO` denies (MEASURED). Nothing in the runtime can change that; the fix is a guest address base inside FEX (JIT memory operands `[xBASE, wADDR, uxtw]`, allocator offset, compat pointer translation, signal frames, thunk pointers) — the largest single piece of FEX work in this plan, and the gate for the Steam client and for pressure-vessel's non-PIE tools.

**15. How FEX integrates Wine.** Two ways exist in the tree.
