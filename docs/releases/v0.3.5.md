**Steam is no longer closed by the memory guard under normal use ("Steam terminó con la señal 9").** Up to 0.3.4 the guard stopped every Linux program as soon as free memory read under 35 % once, which on a 16 GB Mac happened with Steam alone (2.7 GB) and a few other apps open. On memory pressure it now acts only when macOS reports critical pressure for 2 s, or free memory stays under 12 % for 3 s; it stops the largest program first (usually the game), and the rest only if the pressure lasts 5 s more. Its hard limits are unchanged and still stop every Linux program at once, however much memory is free: all of them together above **Sistema → DRAM**, fseventsd above 1500 MB, more than 80 Linux processes, or the kernel's VM objects or map entries above 1,500,000. Either way the launcher now says "El guardián de memoria detuvo Steam" and why, instead of a bare signal 9 (details in `docs/TROUBLESHOOTING.md`).

**Valve's native arm64 Steam client reaches its sign-in window (experimental, a separate app).** Two new entries in the launcher, next to **Steam**:

- **Steam ARM64 (experimental)**, on a Fedora aarch64 root (`scripts/mkarmroot.sh`);
- **Steam ARM64 · Steam Frame (experimental)**, on a root derived from your own Steam Frame recovery image (`scripts/mkframeroot.sh`; the image's files are never shipped).

Both run Valve's aarch64 client with no FEX and no virtual machine, with its web UI's JavaScript JIT on. Measured on a Mac mini M4: from the launcher, the "Sign in to Steam" window appears after 15-16 s (Fedora root) and 21 s (Steam Frame root), and **Detener** leaves nothing running. **Not verified:** signing in, the library, downloads and games under this client; Proton ARM64 does not run on macOS. **Instalar** does not set these entries up: each card stays disabled, with the reason, until its root and the client exist (`docs/STEAM_ARM64_BRINGUP.md`). To play, keep using **Steam**, which is still the x86 client under FEX.

**KosmicKrisp can be picked as the Vulkan driver (experimental).** **Configuración → Gráficos → Motor → Vulkan (KosmicKrisp)** loads Mesa's Vulkan-on-Metal driver instead of MoltenVK. It is offered only when Homebrew's `mesa` is installed (macOS 26 or later) and the installed Vulkan shim can load it; **Instalar** installs that shim. In the Direct3D test probes it runs D3D11 at 158 fps and D3D12 at 154 fps (MoltenVK in the same session: 154 and 158). The shim now reports `fillModeNonSolid`, without which DXVK rejects KosmicKrisp's GPU. Not tried through Steam's own launch path or with any game. MoltenVK stays the default.

Launcher:

- **Library**: search; filters Todas, Favoritas, Recientes, ARM64, x86 and Windows; favourites; each card shows its last launch, how many times it ran and for how long; right-click to open, see its settings, open its folder or logs, mark it as a favourite, or delete it (added apps only).
- **Sessions**: the launcher takes its one-app lock before anything starts, and reports how an app ended from its real exit status. The running panel shows the architecture and translator (aarch64 with none, or x86 with FEX) and "Modo de sesión: ZERO-VM".
- **Settings**: one **Sincronización** choice for Proton (fsync and MSync disabled with the reason, esync experimental), the graphics engine, what to do when a setting cannot work for an app (AUTO, ESTRICTO, PREGUNTAR), and a read-only **Runtime** page with every backend, its state and why. Apple Hypervisor and Lightning JIT are listed as unavailable; no choice uses a virtual machine. An added app can override display, V-Sync, synchronization and graphics engine.
- **V-Sync ON/OFF now reaches VKD3D-Proton (D3D12).** The value was written in lower case, which VKD3D-Proton ignores. Fixed in the settings; its effect in a game is not measured.
- **Añadir app** reads the program first: an aarch64 program goes to the ARM64 root and runs without FEX.

Runtime safety fixes:

- **A site the rewriter refuses now really traps.** Up to 0.3.4 the "poison" word was `svc #1`, which macOS runs as whatever system call a register happens to name: a silent random system call instead of a crash. It is now `brk #1`.
- More instructions that use the x18 register are rewritten instead of refused (ordered loads and stores, flag and FP-status moves, stack-pointer writes); Valve's client and its web UI hit these.
- Memory that native aarch64 programs map read-write-execute (JIT engines) is kept writable or executable per page, never both, and every page is checked before it runs. The runtime also keeps its own fault handling when a program resets SIGSEGV/SIGBUS to the default.
- A program whose code writes into its own 16 KiB page no longer hangs: the store is performed by the runtime, and code written that way is checked before it runs.
- `/proc/self/exe` is an absolute, openable path even when a program was started by a relative one.
- `mmap` of a file at a 4 KiB offset, a thread-exit race, and crash reports that now name the fault address and, for crashes inside macOS code, the calling functions.

Known issues:

- In the post-merge check, 1 of 5 x86 Steam starts died at start with a trap inside macOS code (`pthread_jit_write_protect_np`); cause unknown. Start Steam again. The next such report names the calling code.
- The native client once (1 of 10 launcher starts, stage 23) showed no window because a web UI process crashed at start; stop and start it again. On the Steam Frame root the first web UI process restarts once and two of its processes stay alive until you stop the client, and it starts about 5-7 s later than on the Fedora root.
- The native client's web UI draws in software: its GPU process cannot use OpenGL on the Mac's X server.

Tested on a real Mac (M4, macOS 27) after merging: the x86 Steam client reached its main window in 88-93 s in 4 of 5 starts. tests/elf 64/64 (0 expected failures), tests/elf i386 18/18 (plus 1 existing expected failure), tests/win 11/11 (D3D9/11/12 probes 158.7-161.9 fps, 64- and 32-bit), Steam's container 2/2, ARM64 client checks 4/4, Vulkan device 2/2, launcher core all passing. Records: `benchmarks/stage22-*.txt`, `benchmarks/stage23-*.txt` and `benchmarks/README.md` ("After stage 23").
