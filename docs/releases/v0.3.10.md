**Web pages inside Android apps (WebView).** Apps that show web content through Android's WebView now work: Chromium's page renderer, which Android runs as a separate, sandboxed process, starts under SteamARM, runs JavaScript and draws the page (measured with the image's own WebView, Chrome 137). Many apps are partly web pages, and Google's sign-in needs this too.

**Android apps open more reliably.** About one Android start in ten, Android's app launcher process (the zygote) stopped right after booting and took the system with it, so the app you opened did not install or never came to the front. The cause was one of SteamARM's own internal files showing up where Android checks its open files. Fixed: 10 of 10 quick restarts clean afterwards.

**Runtime:** the Linux features WebView's renderer needed: temporary file systems (tmpfs) in a process's own view of the files, abstract socket names reported back correctly, a queued signal's details delivered with it, no_new_privs remembered, shared-memory seals kept across processes, and EFAULT for a write into a read-only 4 KiB page. FEX (the x86 emulator) no longer runs a system call that a sandbox filter has trapped; an updated FEX reaches your existing Android root by itself.

**Tested on a real Mac (M4, macOS 27) on the release commit's runtime:** tests/elf 97/97; i386 18/18; Windows D3D9/11/12 probes 11/11; Vulkan device 2/2; ARM64 client checks 4/4; launcher core 35/35; the native display server 4/4; Android 85 passed with 2 expected failures (arm64 ART's heap; the headless boot's display wall), WebView, clipboard, per-app windows, sound, network, clicks and keys included. Steam from the launcher: native ARM64 sign-in window 6 of 6 (15-16 s); x86 main window 5 of 6 (71-101 s; once the 32-bit client crashed at the same place it has crashed a few times before, cause not yet known: start it again).
