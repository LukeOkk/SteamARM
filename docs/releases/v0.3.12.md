**Every Android app gets its Mac window, every time.** About one launch in five, an Android app opened (it had the focus) but no Mac window appeared, and sometimes Android's system process hung soon after and kept restarting until the Android session was stopped (0.3.11 listed this as "Known" after Termux). The cause was a race inside the Android image's own window composer, which could wait forever for an answer it had already been given; SteamARM's window server now nudges it out of that wait. Measured: a window in 12 launches of 12 (before: no window in 5 of 28).

**Apps tried:** VLC, Organic Maps, NewPipe, KeePassDX, Wikipedia and Element (all from F-Droid, all with x86-64 native code) install and open. Android's own media player plays H.264/AAC video with sound in real time. VLC opens a video and decodes it but its player stays paused (not yet explained).

**Fewer crashes at start-up:** Android's system tracing app (Traceur) no longer crashes at every boot, and installing an app right after Android starts no longer fails because Android's package manager was not ready yet.

**Tested on a real Mac (M4, macOS 27):** tests/elf 99/99; the native display server 4/4; Python OK; Android 87 passed with 2 expected failures (per-app windows, clipboard and WebView included). Steam's code paths did not change since 0.3.11 (ARM64 sign-in window 8 of 8; x86 main window 5 of 6). Record: `benchmarks/stage35-android-apps-windows.txt`.
