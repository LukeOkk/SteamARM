**Android apps take the Mac's mouse and keyboard, and reach the Internet.** Clicks and keys in an Android app's window now arrive in the app: measured with Simple Solitaire Collection, a click opens a game, Escape is Android's Back and letters arrive as themselves. Android now has a network, the Mac's: apps see an Ethernet connection that Android itself checks and marks as working (validated), names resolve through the Mac, and HTTPS works from inside Android. The window is titled with the app's name, and Android's clock follows the Mac's time zone.

**Split APKs install.** **Añadir APK** accepts XAPK, APKS and APKM files (apps split by Google Play's bundle system, as APK sites offer them): SteamARM installs the base and the parts a Mac needs (the x86-64 part, the screen density, the language). Measured with a real XAPK (a base and a density split): installed in one step and started. AAB files are still refused (they need Google's bundle tool and a signing key).

**32-bit Android programs run.** Android's 32-bit (x86) programs refused to start whenever the Mac had handed out process numbers above 65535, which is most of the day. SteamARM now gives every Android process and thread a small number of its own: the 32-bit Java runtime, compiler, secondary app loader and system services run (measured: every such check in the test suite passes).

**Sound from Android (first step).** A session with a window plays to the Mac through SteamARM's PulseAudio: raw sound from an app reaches the speakers (measured). Sound from compressed files (most games' effects and music, system sounds) does not play yet: Android's decoders here depend on a 32-bit media service that does not run under SteamARM yet.

**Experimental: Android in a native Mac window.** `steamarm-wlmac`, a Wayland display server written for macOS, can replace the Linux one for Android sessions (`ANDROID_SESSION_COMPOSITOR=wlmac`): Android then shows its desktop mode, apps in movable windows, in one native Mac window. One Mac window per Android app is not there yet.

**Runtime:**
- POSIX timers (`timer_create`): Android's media extractor needed them.
- SteamARM's X server numbers keys as Linux does (Chromium, Electron and Android assume it) and has the XTEST extension (Steam Input's desktop mode uses it). Both take effect when the X server starts again; **Instalar** restarts it when nothing is running.
- Android sessions no longer leave FEX servers behind.

**Google Play Store:** still not run; its network requirement is now met. SteamARM still never downloads or bundles Google's apps.

**Tested on a real Mac (M4, macOS 27) on the release commit's runtime:** tests/elf 88/88; i386 18/18; Windows D3D9/11/12 probes 11/11 at 159-162 fps; Vulkan device 2/2; ARM64 client checks 4/4; launcher core 35/35; the native display server 3/3; Android 80 passed with 2 expected failures (arm64 ART's heap; the headless boot's display wall), clicks, keys and network included. Steam from the launcher: native ARM64 sign-in window at 16 s (Fedora root) and 20 s (Steam Frame root); x86 Steam main window at 91 s in 2 of 3 starts (the first, right after other sessions, showed no window in 5 minutes: stop and start it again). Steam's container: sound passes; the XInput controller probe is intermittent (3 of 6 runs; 3 of 4 with 0.3.6's runtime). Records: `benchmarks/stage29-android-input-network.txt`.
